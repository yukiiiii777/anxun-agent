# 价值指标口径 · 唯一事实来源

> **这份文件是干什么的**：v2.0 新增了五个运营指标，第一次报出去就会被追问
> 「这个数怎么算的、样本多少、能不能复现」。和 `docs/技术口径.md` 一样的规矩——
> **PPT、视频、答辩稿、README 引用这五个数，以本文为准**；本文与
> `data/value_metrics.json` 不一致时，先跑脚本重算，再改本文，顺序不能反。
>
> 最后核对：2026-11-02 ｜ 对应版本 `techline-v2.0.0`

---

## 一、账本：v2.0 的数据基础

v1.x 只在判违规时落一条事件，合规的人一条记录都不留。所以「合规率」没有分母。
v2.0 在 `stream.py` 的 `StreamPipeline` 里加了判定账本，**每一次定论都记**，
不论合规与否。

| 字段 | 含义 | 备注 |
| :--- | :--- | :--- |
| `track` | 轨迹编号 `T1` / `T2`… | IoU 贪心匹配，连丢 2 帧删轨 |
| `equip` | `helmet` / `vest` | 一人多装备 = 多条记录 |
| `status` | `已佩戴` / `未佩戴` / `待复核` / `无法判定` | 与 `Verdict.status` 同源 |
| `t_video_s` | 该状态**第一次**成立的视频时刻 | |
| `t_last` | 该状态**最后一次**仍成立的时刻 | 与上者之差 = 持续时长 |
| `violation` | 是否违规 | 等价于 `status == 未佩戴` |
| `observations` | 这个状态被观测到几次 | 单帧素材下用它兜底选主导状态 |

**为什么按「状态变化」记，不逐帧记**：2fps × 60s = 120 条/路；一个 20 路园区
跑一天就是 345 万条，账本自己先成了负担。按状态变化记，条数等于「这个人换了
几次状态」，量级才对得上运营口径。

**关闭方式**：`stream.py --no-ledger` 退回 v1.x 行为（只出违规事件）。

## 二、五个指标

样本基线（本文所有数字的出处）：

| 项 | 值 |
| :--- | :--- |
| 素材 | `datasets/site_demo.mp4`（60s / 720p / B-01）+ `datasets/real1080.mp4`（100s / 1080p / A-03） |
| 总时长 | 160 秒 |
| 出现人次 | 81（轨迹数，不等于独立人数） |
| 逐帧告警 | 550 次 |
| 去重后事件 | 56 条 |
| 账本 | 115 条 |

### 2.1 巡检覆盖率 · 16×

```
巡检覆盖率 = 系统看得见的时长 / 人工看得见的时长
           = (路数 × 单路连续小时 × 60) / (每班次数 × 每次分钟数)
           = (1 × 8 × 60) / (2 × 15) = 480 / 30 = 16
```

| 项 | 说明 |
| :--- | :--- |
| **⚠️ 这是推演值，不是实测** | 人工侧是**排班假设**（每班 2 次、每次 15 分钟），不是我们观测到的 |
| 可调参数 | `stats.py --hours 8 --manual-times 2 --manual-minutes 15` |
| 系统侧为什么算「全时长」 | 摄像头一直开着，静止跳过只是跳过推理，不是没看 |
| 换真实制度后 | 把三个参数改成现场实际值重算，其余不变 |

**答辩措辞**：「按每班两次、每次十五分钟的巡班制度折算，单路摄像头相当于
把可见时长从 30 分钟提到 480 分钟，16 倍。这是排班推演，不是实测覆盖率。」

### 2.2 判定覆盖率 · 60.5%

```
判定覆盖率 = 有定论的轨迹 / 进入画面的人次 = 49 / 81 = 60.5%
```

| 项 | 说明 |
| :--- | :--- |
| 「有定论」 | 该轨迹凑满三帧、时序聚合给出了结论（不论合规还是违规） |
| **v1.x 看不见这个数** | 只报违规，没人管「多少人根本没被判定」 |
| 低说明什么 | 轨迹碎片化：目标小、走得快、IoU 匹配断掉就重新开轨，三帧窗口凑不齐 |
| 不是模型不准 | 模型再准，判不到的人也进不了合规率分母 |

**分组实测**：

| 素材 | 分辨率 | 出现人次 | 有定论 | 判定覆盖率 |
| :--- | :--- | ---: | ---: | ---: |
| `site_demo.mp4` | 720p | 37 | 5 | **13.5%** |
| `real1080.mp4` | 1080p | 44 | 44 | **100%** |

同一套代码、同一个阈值，720p 只有 13.5%、1080p 是 100%。**结论是素材/机位问题，
不是换模型能解决的**——这条差异本身就是 v2.0 想让人看见的东西。

### 2.3 告警降噪率 · 89.8%

```
告警降噪率 = 1 − 事件数 / 逐帧告警数 = 1 − 56 / 550 = 89.8%
```

| 项 | 说明 |
| :--- | :--- |
| 分子 | 冷却去重后的事件（同一人同一违规，冷却期内只报一次） |
| 分母 | 三帧定论后、逐帧判违规的次数（`stats.raw_alarms`） |
| 衡量什么 | 「一个人站十分钟只报一次」这件事到底省了多少 |
| 与 v1.x 的关系 | v1.x 也能算，但没记 `raw_alarms`，所以一直没算过 |

分素材：`real1080` 单段 538 → 50（90.7%），`site_demo` 单段 12 → 6（50%）。
后者样本太小（12 次告警），别单独引用。

### 2.4 合规率 · 4.7%

```
合规率 = 合规人次 / 可判定人次 = 2 / 43 = 4.7%
```

| 项 | 说明 |
| :--- | :--- |
| 一个人算一次 | 同一轨迹的每种装备先收敛成**主导状态**（累计观测时长最长的那个），再判 |
| 有一样违规就算违规 | 戴了帽子没穿背心 = 违规，不能算「部分合规」 |
| 分母排除什么 | `待复核` 4 人次、`无法判定` 2 人次，**不进分母**（与误报率的 `matched` 口径同源） |
| 为什么不能按账本条数算 | 一个人从「待复核」抖到「已佩戴」再抖回来会产生三条记录，按条数算等于让抖得厉害的人占更大权重 |

> ⚠️ **4.7% 不能当「现场合规水平」引用**。这两段素材本身就是违规演示素材
> （`real_violation` / `site_demo` 里的违规片段），不是随机抽样。合规率这个
> 指标的意义在于**口径成立**（换真实班次数据直接能算），不在于这个数好看。

### 2.5 违规持续时长 · P50 3.5s / P95 13.5s

```
违规持续时长 = t_last − t_video_s   （仅取 violation = true 的记录）
P50 = 3.5s · P95 = 13.5s · 最长 = 13.5s · n = 54
```

| 项 | 说明 |
| :--- | :--- |
| **⚠️ 这是「闭环时长」的降级口径** | 素材里只有人走过，没有「戴上帽子再走」的整改动作 |
| 真实现场怎么升级 | 账本里只要出现一条 `已佩戴`，同轨迹的「违规 → 合规」之差就是整改耗时，**口径不用改** |
| 排除了什么 | 时长为 0 的瞬时记录（单帧判定），它们不构成「持续」 |

**答辩措辞**：「这次素材没有整改过程，所以报的是单次告警的持续时间，中位 3.5 秒。
真实班次数据接进来后，同一个账本自动能算『违规到整改』的耗时，不用改代码。」

## 三、与 v1.2.0 四个指标的关系

**没有任何关系，互不影响。** v2.0 不碰模型、不碰阈值、不重测：

| v1.2.0 指标 | v2.0 后是否变化 |
| :--- | :--- |
| mAP@0.5 = 0.681 | **不变** |
| 误报率 6.12% | **不变** |
| 漏报率 17.20% | **不变** |
| 单帧 46 ms (CPU) / 22 ms (GPU) | **不变** |

价值指标是**在判定结果之上加的一层**：`judge_frame` 返回什么，账本就记什么。
验收脚本有一条专门盯这个——「事件文件含全量判定账本」+「账本自洽」，
改造过程中 `events` 与 v1.2.0 逐字段比对过，零漂移。

## 四、已知局限（引用数字时必须一并说明）

1. **样本 160 秒 / 81 人次，属演示级样本。** 100 张测试集能分辨「差一个量级」，
   分辨不了「差一两个点」（见 `docs/指标置信区间.md`）。价值指标同理，别外推。
2. **巡检覆盖率是排班推演。** 人工基线是假设值。
3. **违规持续时长不是整改时长。** 素材无整改过程。
4. **合规率 4.7% 来自违规演示素材。** 不代表现场水平，只证明口径成立。
5. **人次 ≠ 人数。** 一个人走出画面再进来会得到新轨迹，计两次。
6. **账本按状态变化记，不是按帧记。** 想要逐帧明细请用 `--no-ledger` 之外的原始事件流。

## 五、复现

> `datasets/site_demo.mp4`（8.8 MB）随仓库分发，第 1 条命令 clone 下来直接能跑。
> `datasets/real1080.mp4`（59 MB）体积太大不入库，先跑 `python tools/make_1080_stream.py` 重建；
> 一时不想重建 `--events` 里只给 `events_site.json` 也能出结果，只是判定覆盖率会掉到 13.5%
> （720p 轨迹碎片化，见 2.2），不是代码问题。

```bash
# 1. 账本（两段素材，两个区域）
python src/anxun/stream.py --source datasets/site_demo.mp4 --fps 2 --region B-01 --out data/events_site.json
python src/anxun/stream.py --source datasets/real1080.mp4 --fps 2 --region A-03 --out data/events_1080.json

# 2. 五个指标
python src/anxun/stats.py --events data/events_site.json data/events_1080.json \
                          --out data/value_metrics.json

# 3. 报告
python src/anxun/report.py --metrics data/value_metrics.json \
                           --events  data/events_site.json data/events_1080.json \
                           --out     docs/figs/value_report.html

# 4. 验收（含账本自洽、指标齐全、报告与 JSON 一致、README 与 JSON 一致）
python src/anxun/verify_all.py
```

跑出来的数应与 `data/value_metrics.json` 逐位一致。若不一致，先查
`config/thresholds.json` 的 profile 是否为 `measured`（`conservative` 会改变判定，
进而改变账本）。
