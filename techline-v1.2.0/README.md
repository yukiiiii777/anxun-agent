## 一、概述

### 1.1 目标

将「摄像头看到的违规」转化为「有责任人、有等级、有时限、可验收的工单」。技术线承担其中
可交付、可验证的部分：模型可运行、指标可复现、部署可移植、技术页可直接使用。

### 1.2 交付范围

本交付物包含：检测模型与推理后端、确定性判定规则、风险定级与工单生成、评测与验收脚本、
视频巡查与多路调度、HTTP 推理服务、技术页素材。

不在本交付物范围内：前端界面、工单流转系统、多智能体对话编排。

## 二、系统架构

### 2.1 分层设计

```
图像 / 视频
   │
   ├─ 检测层  三模型串联：person → helmet → vest        模型只产框，不做判断
   │
   ├─ 判定层  四态判定 + 时序聚合 + 反向证据             纯确定性规则，同一输入同一输出
   │
   ├─ 定级层  R = L（近 30 天违规频次）× S（违规类型 × 作业场景）
   │
   └─ 输出    结构化 JSON：判定、事件、工单、法规依据
```

三条设计约束：

1. **检测与判定解耦**：模型只产出 `Box`，规则引擎不依赖任何模型实现，更换模型不影响业务逻辑；
2. **判定不使用大模型**：全部为确定性计算，可复现、可审计、可当场重算；
3. **结论可解释**：每条判定与每个等级均携带 `reason` 与 `L/S/R` 推导过程。

### 2.2 模块职责

| 模块 | 职责 |
| :--- | :--- |
| `rules_engine.py` | 四态判定、时序聚合、风险矩阵、工单生成（纯标准库） |
| `detectors.py` | 三模型串联、类别映射、人员门控、批前向 |
| `pipeline.py` | 单图链路：检测 → 判定 → 定级 → 工单 |
| `stream.py` | 单路视频：三级触发 + 判定状态机 + 跨帧跟踪 |
| `scheduler.py` | 多路视频：锁步攒批 + 各路独立状态机 |
| `backend.py` | 后端分发：有显卡用 torch-CUDA，无显卡用 ONNX-CPU |
| `onnx_backend.py` | ONNX 推理实现（letterbox / 解码 / NMS，不依赖 torch） |
| `metrics.py` | mAP@0.5、误报率、漏报率、耗时与 PR 曲线 |
| `evaluate_real.py` | 真实照片评测，指标数字的唯一来源 |
| `app.py` | HTTP 推理服务 |
| `verify_all.py` | 交付物验收（47 项） |

## 四、模型

### 4.1 模型组成

| 权重 | 用途 | 结构 | 输出类别 | 体积 | 来源 | 自训 |
| :--- | :--- | :--- | :--- | ---: | :--- | :---: |
| `models/yolov8n.pt` | 人体检测 | YOLOv8n（COCO 80 类） | `person` | 6.55 MB | 公开权重 | 否 |
| `models/best.pt` | 安全帽检测 | YOLOv8s 微调 | `Hardhat` / `NO-Hardhat` | 22.49 MB | 公开权重 | 否 |
| `models/vest.pt` | 反光背心检测 | YOLOv8n 微调 | `vest` / `no_vest` | 6.26 MB | 本项目训练 | 是 |

拆分为三个模型的原因：公开的安全帽权重只含 `Hardhat` / `NO-Hardhat` 两类，不含 `person`；
单模型推理时每张图均判定为「0 人」，判定链第一步即中断。拆分后任一模型均可独立替换。

对外表述应为「公开权重 + 自训背心模型组成三模型串联」，不宜表述为「训练了安全帽模型」。

权重指纹（SHA256）与获取方式见 `docs/模型卡片.md`。`.onnx` 为 `.pt` 的导出快照，
修改 `.pt` 后必须重新导出，否则会出现「可移植版运行旧模型」的静默错误。

### 4.2 架构选型

同一输入尺寸（640）、随机初始化权重、15 次中位数，仅比较架构开销：

| 架构 | 参数量 | FLOPs | CPU 延迟 | 结论 |
| :--- | ---: | ---: | ---: | :--- |
| yolov8n | 3.16 M | 8.9 G | 44.2 ms | 现用（人体） |
| yolov8s | 11.17 M | 28.8 G | 97.6 ms | 现用（安全帽） |
| yolo11n | 2.62 M | 6.6 G | 41.4 ms | 同规模最省 |
| yolo11s | 9.46 M | 21.7 G | 88.7 ms | 重训首选 |
| yolo12n | 2.60 M | 6.7 G | 52.9 ms | attention 在 CPU 上更慢 |
| yolo26n | 2.57 M | 6.1 G | 43.9 ms | FLOPs 最低，CPU 无优势 |

数据：`data/arch_bench.json`（随机权重，仅比较架构开销，不含精度）。

### 4.3 当前仍采用 YOLOv8 的依据

架构层面 YOLO11 更优（同规模 FLOPs −26%、CPU 延迟 −6%），但当前不具备切换条件：

**（1）三个权重均为 v8 结构。** `.pt` 不跨版本兼容，切换架构意味着三个模型全部重训或重找；
安全帽一类没有公开的 v11 版本可用，而本项目自采数据为 0。

**（2）同架构重训已验证，业务指标下降。** 在 `helmet_p2` 1300 张上微调 v8s：

| 权重 | helmet AP | 误报率 | 漏报率 |
| :--- | ---: | ---: | ---: |
| 公开权重 | 0.5645 | **5.10%** | **24.7%** |
| 同架构微调 1300 张 | 0.7376 | 17.4% | 32.3% |

> 该对比在当时的几何阈值（0.25 / 0.60）下完成，用于比较两个权重；现行几何（0.28 / 0.70）的指标见 6.2。

检测级 AP 提升 31%，业务指标全面变差。根因是框的几何变化：帽框 / 头部区域 IoU 由 0.410 降至 0.291、
框面积比由 0.86 降至 0.60，而判定阈值按原权重的框几何标定。更换架构将在该问题之上叠加未知变量
（v11 的框回归风格与置信度分布均未测量）。

**（3）切换成本与收益不对等。** 收益为 CPU 延迟 −6%（44.2 → 41.4 ms），落到三模型交付路径上
约相当于 25 路变 26 路；成本为四个指标重测、两套阈值重扫、ONNX 一致性重验、全部文档重写。

**（4）YOLO11 的优势不在本项目瓶颈上。** 其增益集中于 COCO 通用 mAP 与参数效率；本项目瓶颈为
helmet 类 AP 0.5645（公开权重上限）与域偏移，而非骨干网络。小目标漏检需通过 P2 检测头或提高
输入分辨率解决，代价为算力 +56%。

切换条件（满足任一即可启动）：自采数据到位且重训后业务指标可追平 6.12% / 17.20%；路数成为瓶颈、
需上 TensorRT；重训窗口开放。切换时按「重训 → 重扫两套阈值 → 重测四指标 → 重验 ONNX 一致性」
四步执行，缺任一步则数字不可比。

## 五、判定规则

### 5.1 四态判定

单人单类装备的判定链共五步：

1. **可用性检查**：人员框面积低于阈值，或高宽比低于 0.90（疑似半身 / 蹲姿）→ `无法判定`；
2. **区域圈定**：安全帽取人员框上部 30%、横向居中 44%；反光背心取 20%–70% 高度；护目镜取上部 45%；
3. **匹配**：与同类装备框计算 IoU 与包含度，两者任一达标即视为命中；
4. **反向证据**：`nohelmet` / `novest` 框参与判断，正反证据同时高置信时转 `待复核`；
5. **置信度分档**：≥ `conf_final` 定论；`[conf_review, conf_final)` 转待复核；< `conf_review` 丢弃。

输出四态：`已佩戴` / `未佩戴` / `待复核` / `无法判定`；置信度过低时另有 `丢弃`，不进入统计。

两个关键设计点：

- **头部区域横向收窄至 44%**：安全帽框约占人员框宽 42%，若按整宽取上部 30%，正常佩戴的 IoU
  恒为 0.18，无法达到 0.30 阈值；
- **并列使用包含度判据**：护目镜一类小目标框面积仅为面部区域的 8%，IoU 在数学上无法达标，
  以包含度 ≥ 0.60 作为并列条件。

### 5.2 阈值口径

阈值唯一定义在 `config/thresholds.json`，代码、文档、验收脚本均读取该文件。

| 参数 | `measured`（交付与评测） | `conservative`（演示） |
| :--- | ---: | ---: |
| `conf_final` | 0.30 | 0.60 |
| `conf_review` | 0.20 | 0.40 |
| `helmet.iou_min` / `contain_min` / `max_ratio` | 0.25 / 0.60 / 3.0 | 0.30 / 0.60 / 3.0 |
| `vest.iou_min` / `contain_min` / `max_ratio` | 0.10 / 0.60 / 6.0 | 0.30 / 0.60 / 6.0 |
| `head_region_ratio` / `head_width_ratio` | 0.30 / 0.44 | 0.30 / 0.44 |
| `min_person_area` / `min_aspect` | 8000 px² / 0.90 | 8000 px² / 0.90 |

`min_person_area` 为 1920×1080 标定值，运行时按画面面积占比换算，与分辨率解耦。
口径切换方法与影响见 `docs/技术口径.md` 第一节：交付与评审使用 `measured`，演示若使用
`conservative` 必须同时声明。

### 5.3 风险定级

```
R = L × S
L：该区域近 30 天违规次数 → ≤1 取 1，≤3 取 2，≤6 取 3，其余取 4
S：违规类型 × 作业场景（高处未戴帽 4、动火 3、车辆通行未穿背心 3、普通 3 / 2 …）
```

| 风险值 | 等级 | 处置要求 | 整改时限 |
| :--- | :--- | :--- | :--- |
| ≥ 12 | 红色 | 立即停止作业并整改 | 2 小时 |
| ≥ 8 | 橙色 | 当日整改 | 24 小时 |
| ≥ 4 | 黄色 | 限期整改 | 7 天 |
| ≥ 0 | 蓝色 | 加强关注 | 30 天 |

同一违规在不同场景下等级不同（例：未戴安全帽在普通通道为黄色，在高处作业平台为橙色），
这是定级机制的主要验证点。

### 5.4 工单

每张工单包含：违规类型与数量、责任区域与责任人、整改要求（物资 + 地点 + 留痕动作）、
等级与时限、50% 时限升级点、复查时间（整改完成次日）、法规依据。

法规依据仅收录逐条核对过的条款；标准类文件只登记标准号与适用范围，不伪造条文原文；
检索不到时明确输出「未检索到直接对应条款」。

### 5.5 时序聚合

视频流按「连续 3 帧结论一致」定论；不足 3 帧或帧间结论不一致时转 `待复核`。视频链路以
「一条轨迹一个窗口」组织，同一人的判定项顺序稳定；若多帧场景的判定项数不一致，整体转人工，
不按下标强行比较。单张照片不做时序聚合。

## 六、指标

### 6.1 定义

| 指标 | 定义 | 层级 |
| :--- | :--- | :--- |
| mAP@0.5 | 逐类贪心匹配、IoU 阈值 0.5 的全点插值 AP 均值 | 检测层 |
| 误报率 | 实际合规却判「未佩戴」的人×装备 / 实际合规总数 | 业务层 |
| 漏报率 | 实际违规却未判「未佩戴」的人×装备 / 实际违规总数 | 业务层 |
| 单帧耗时 | `evaluate_real.py` 在 100 张测试集上的均值（含前后处理） | 工程层 |

误报率与漏报率按**人×装备**统计，不按框统计。

业务指标另有两种统计范围，评测脚本同时输出：

- `matched`（默认，交付数字）：只统计被检出的人，衡量判定层；
- `e2e`：连未被检出的人一并计入，衡量整条链路。

### 6.2 实测结果

测试条件：`yolov8n + best + vest` 三模型、imgsz 640、conf 0.25、`measured` 口径、RTX 5060。

| 指标 | 数值 | 目标 | 判定 |
| :--- | ---: | ---: | :--- |
| mAP@0.5 | **0.6808** | ≥ 0.85 | 未达标 |
| 误报率 | **6.12%**（6/98） | ≤ 10% | 达标 |
| 漏报率 | **17.20%**（16/93） | ≤ 5% | 未达标，收敛中 |
| 单帧耗时（GPU） | **≈22 ms**（p95 ≈25） | ≤ 50 ms | 达标 |

记作 **6.1% / 17.20%**，与验收脚本的比对口径一致。混淆矩阵：`tp 77 / fn 16 / fp 6 / tn 92`；
逐类 AP：`person 0.7971`、`helmet 0.5645`。

按整条链路口径重算：误报 **5.61%**（6/107）、漏报 **26.67%**（28/105）。真值可判 212 人次，
实际进入统计 191 人次，覆盖率 90.1%，差额为检测层未匹配上的人。对外引用 17.20% 时须同时
说明统计范围为「已检出人员」。

**置信区间**（Wilson 95%，按人次）：

| 指标 | 点估计 | 95% 区间 | 表述 |
| :--- | ---: | :---: | :--- |
| 误报率 | 6.12% | 2.8–12.7% | 点估计达标，区间上界越线，不宜表述为稳定达标 |
| 漏报率 | 17.20% | 10.9–26.1% | 区间下界仍高于 5%，差距非样本量所致 |

**分辨率稳健性**：同一批 100 张 3 倍上采样至 1920×1920 复测，mAP 0.6829、误报 7.14%、
漏报 18.28%、单帧 41.5 ms。误报不变说明判定链对分辨率不敏感，漏报上升来自上采样插值失真。
该素材为上采样结果，不等同于真实 1080p 录像。

### 6.3 配置选型

同一测试集、仅改变模型规模与输入尺寸（耗时列为 torch-CPU 实测，为阈值优化前的基线）：

| 配置 | mAP@0.5 | helmet AP | 误报率 | 漏报率 | 单帧耗时 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| s @480 | 0.685 | 0.562 | 15.8% | 34.5% | 89.5 ms |
| **s @640（默认）** | **0.688** | **0.579** | **11.2%** | 38.7% | 138 ms |
| s @960 | 0.654 | 0.515 | 17.0% | 45.2% | 308 ms |
| m @480 | 0.569 | 0.331 | 15.8% | 37.9% | 170 ms |
| m @640 | 0.547 | 0.297 | 18.4% | 38.7% | 283 ms |
| m @960 | 0.545 | 0.297 | 16.0% | 40.9% | 637 ms |

两条结论：**更大的模型不一定更好**（m 版权重来自另一版本数据，类别口径与现场图不匹配，
需按实测而非模型大小选型）；**提高分辨率不一定更好**（权重在 640 上训练，放大推理使目标
偏离训练分布）。当前 s @640 为该批权重的最优点；阈值优化后的指标见 6.2。

### 6.4 耗时口径

| 路径 | 设备 | 单帧均值 | p95 | 出处 |
| :--- | :--- | ---: | ---: | :--- |
| torch + CUDA | RTX 5060 | **≈22 ms** | ≈25 ms | `data/metrics_real.json` |
| ONNX + CPU | 24 线程 | **≈45 ms** | ≈49 ms | `data/metrics_onnx.json` |
| ONNX + CPU（优化前） | 同上 | 72.7 ms | 82.4 ms | 历史值，已作废 |

三模型同时运行的代价约 32 ms（`data/metrics_vest.json`）。耗时随 GPU 时钟与后台负载波动，
文档统一写近似值，精确值以 JSON 的 `latency.mean_ms` 为准。

### 6.5 优化记录

效果按当时口径记录，现行数字见 6.2。

| 措施 | 效果 | 代价 |
| :--- | :--- | :--- |
| 人员门控（无人帧不跑装备模型） | 前向次数显著下降 | 检测级 mAP 0.688 → 0.681，业务三项不变 |
| 按装备分离几何阈值 | helmet 5.10% / 24.7%；vest 27.3% / 13.0% | 两套参数，需分别维护 |
| 置信度阈值扫参 | 误报 7.1% → 5.10% | 阈值在测试集上选取，属乐观估计 |
| 高宽比下限 1.20 → 0.90 | 漏报 24.73% → 22.58%，误报不变 | 弯腰作业多一分风险 |
| ONNX 三模型并发 + 预处理复用 | CPU 单帧 72.7 → 45.1 ms | 依赖多核，逻辑线程 ≥12 才启用 |
| 几何阈值复扫（0.25/0.60 → 0.28/0.70） | 漏报 22.58% → **17.20%**，误报 5.10% → 6.12% | 误报多花 1 个点；测试集上调参，乐观偏差更大 |

### 7.1 两种运行形态

| 机器 | 安装 | 运行时 | 单帧 |

### 7.2 安装与启动


### 7.3 接口

| 方法 | 路径 | 用途 |
| :--- | :--- | :--- |
| GET | `/health` | 服务状态、后端、设备、自检耗时、可用能力 |

### 7.4 视频巡查

```bash
# 单路
python src/anxun/stream.py --source rtsp://10.0.0.8/stream1 --fps 2 --region B-01
# 多路
python src/anxun/scheduler.py --sources rtsp://cam1,rtsp://cam2,cam3.mp4 --fps 1 --batch 4
```

链路：三级触发 → 批处理推理 → 三模型检测 → 四态判定 → 跨帧跟踪 → 3 帧定论 → 事件去重。

**三级触发**（固定机位大部分时间为空画面，主要浪费是「计算了不需要计算的帧」）：

| 级别 | 判据 | 节省 |
| :--- | :--- | :--- |
| 一、抽帧 | 2 fps | 600 帧 → 120 次采样 |
| 二、帧差 | 灰度均差 < 10.0 | 120 → 21 次推理（−82.5%） |
| 三、人员门控 | 画面无 `person` | 采样帧中 103/120 无人，省 86% 的装备模型前向 |

三级叠加：240 次前向 → 39 次（−84%），告警结果与全量推理一致。

**1080p 复验**：合成动画上标定的帧差阈值 3.0 在真实机位抖动下会失效（抖动本身使帧差中位数
达 3.862，节省由 90% 降至 39%）。阈值调整至 10.0 后，抖动场景节省回到 86%，告警与全量一致。

**批处理调度**：

| batch | 每帧耗时 | 相对 |
| ---: | ---: | ---: |
| 1 | 19.5 ms | 1.00× |
| 4 | 13.7 ms | **1.40×** |
| 8 | 14.8 ms | 1.32× |
| 16 | 14.1 ms | 1.39× |

batch=4 为当前 GPU 的最优点；瓶颈在 CPU 侧的预处理与后处理，不随批大小摊薄。

## 附录 A 口径速查

| 问题 | 答案 |
| :--- | :--- |
| 判定阈值以哪份为准 | `config/thresholds.json`；文档与代码冲突时以它为准 |

| 换模型或换数据集后要做什么 | 重扫两套阈值 → 重测四指标 → 重验 ONNX 一致性 |
| 为什么不用 YOLO11 | 见 4.3 |
| 为什么 CPU 用 ONNX 不用 torch | 依赖体积与可移植性；CPU 上 ONNX 亦更快 |
| 演示能否改阈值 | 可以，使用 `conservative`，但必须同时声明当前口径 |
