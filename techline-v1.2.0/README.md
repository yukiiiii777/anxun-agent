## 二、跑起来（换台电脑也能跑）

**三种机器，同一份代码，启动命令完全一样：**

| ----------------- | ------------------------------------- | ------------ | ------------- |

| 有 NVIDIA 显卡       | `pip install -r requirements-gpu.txt` | torch + CUDA | **≈22 ms/帧** |
| 有显卡但想省空间          | `pip install onnxruntime-gpu`         | ONNX + CUDA  | 自动识别          |

```bash

./install.sh && ./run.sh          # -> http://127.0.0.1:8765
```

后端**自动选**，不用改代码也不用改参数：有 torch+CUDA 走 GPU，没有就走 ONNX CPU。

|                          |                                  |
| ------------------------ | -------------------------------- |
| 想强制指定就加 \`--backend onnx | torch`，强制 CPU 加 `--device cpu\`。 |

`/health` 会如实报出当前跑的是哪条路，**不静默降级**：

```json
{"backend": "onnx+onnx", "backend_kind": "onnx", "device": "CPUExecutionProvider",

```

### 2.1 为什么要做 ONNX 后端

原来的门槛不是代码，是依赖：

|        | .pt + torch                                            | **.onnx + onnxruntime**                           |
| ------ | ------------------------------------------------------ | ------------------------------------------------- |
| 运行时依赖  | torch 2.14.1+cu130 = **1.99 GB**（cp313 + Blackwell 专用） | onnxruntime + numpy + opencv ≈ **80 MB**          |
| 模型体积   | 28 MB                                                  | **55 MB**                                         |
| 换台电脑   | 基本装不上（Python 版本/显卡架构一换就废）                              | `pip install` 三行搞定，任何平台                           |
| CPU 耗时 | 138 ms                                                 | **≈46 ms**（快 3.0 倍）                              |
| 指标     | —                                                      | **四个数完全一致**（0.6808 / 5.1% / 22.58% / 72-21-5-93） |

ONNX 版是自己实现的 letterbox + 解码 + NMS（`onnx_backend.py`，纯 numpy），  
不依赖 ultralytics 也不依赖 torch。逐框比对过：同一个模型、同一张图，坐标和置信度小数点后两位一致。

> 📌 **耗时口径（v1.2.0 起只有一个）**：单帧耗时 = `evaluate_real.py` 在 100 张测试集上的**均值**，
> 含前后处理，同一后端、同一台机器。ONNX-CPU **≈46 ms**（p95 ≈49）· torch-GPU **≈22 ms**（p95 ≈25，三次复跑 21.8–22.4）。
>
> 旧文档里的 **53.5 ms 已作废**：那组数出自未锁版本的 `onnxruntime`（`>=1.17`），v1.1.0 锁到 1.31.1 后
> 同一模型复测是 72.7 ms；v1.2.0 又把三个模型改成「共享预处理 + 并发」，现在是 ≈46 ms
> （做法与验证见 [`docs/技术口径.md`](docs/技术口径.md) 3.2）。三个数不是同一套代码，不能并列引用。
> 同理，启动自检报的 **8.8 / 31.7 ms** 是「单帧单次」的活性探测，只证明「真的在用 GPU」，
> **不是指标口径**——不要拿它和上表的 ≈22 / ≈46 对比。

### 2.2 踩到的一个大坑：ORT 线程自旋

刚接上 ONNX 时 CPU 单帧要 **833 ms**，比 torch 还慢 6 倍。查下来不是模型问题：

> ONNX Runtime 默认让每个 session 的计算线程**忙等（spin）**&#x800C;不是睡眠。  
> 我们有两个 session（人体 + 装备）交替跑，24 核被 48 个自旋线程抢爆。  
> 加一行 `session.intra_op.allow_spinning = 0` 后：**888 ms → 49 ms，18 倍**。

这行在 `onnx_backend.py` 里带注释，是全文件最重要的一行。

### 2.4 有显卡的机器：自动用显卡，启动时自检并报实测数

后端**自动选**，不用改代码也不用改参数。三个入口（`app.py` / `stream.py` / `scheduler.py`）
启动时都会跑一次自检，把「检测到 CUDA」变成「确实在用、而且这么快」：

```
设备：cuda:0  GPU已启用  实测 8.8 ms/帧
```

或没显卡时：

```
设备：CPUExecutionProvider  GPU未启用  实测 31.7 ms/帧
提示：本机可用后端 {...}  想让 GPU 生效：装 torch 或 onnxruntime-gpu；或加 --device cuda:0
```

`/health` 里也带同样的字段（`selfcheck` + `available`），不用登机器就能确认线上跑在哪。

**为什么要有自检**：光是「检测到 CUDA」不等于「真的在用」——驱动不匹配、
provider 回落、显存不足都会让程序悄悄跑在 CPU 上。自检拿真实帧量一遍，报的是实测值。

> 自检用的是 `datasets/` 里的真实视频帧，不是随机图：随机图没有目标、NMS 不干活，
> 同一后端能差 25%（噪声 23.9 ms vs 真实 31.7 ms）。

实测对比（同一台机、同一批真实帧）：

| 路径 | 设备 | 单帧 | 相对 |
|---|---|---|---|
| `--backend auto` | cuda:0（torch-CUDA） | **8.8 ms** | 1.0× |
| `--device cpu` | CPUExecutionProvider（ONNX） | 31.7 ms | 3.6× 慢 |
| `--backend torch --device cpu` | torch-CPU | ~70 ms | 8× 慢 |

想强制指定：`--backend onnx|torch` 选实现，`--device cpu|cuda:0` 选设备，两者可以组合。

### 2.5 想用 GPU 的话

`onnxruntime`（CPU 版）和 `onnxruntime-gpu` **只能装一个**，装上哪个就跑哪个，代码不用改。

`onnxruntime-gpu` 需要机器上有 CUDA 12.x + cuDNN 9 的运行时。装不上也没关系——  
只要装了 torch 且 CUDA 可用，`auto` 会直接走 torch 那条路，效果一样。

| 接口                                                          | 用途                     |
| ----------------------------------------------------------- | ---------------------- |
| `GET /health`                                               | 服务与模型状态、当前后端、本机可用后端清单  |
| `GET /api/scenes`                                           | 样例场景 + 阈值表             |
| `POST /api/inspect {scene_id}`                              | 完整链路：检测 → 四态 → 定级 → 工单 |
| `POST /detect_b64 {image_base64 \| image_path \| scene_id}` | 只做检测，给扣子插件/外部系统        |
| `GET /api/metrics`                                          | 最近一次评测结果               |
| `GET /docs/<file>`                                          | 技术页等静态文档               |

## 四、模型

**三模型串联**（v1.1.0 起加了反光背心，本节此前写「双模型」，是滞后的表述）：

```
画面 ──> yolov8n (COCO) ──────> person 框 ──────────────────┐
     ├─> yolov8s-hardhat ────> helmet / nohelmet 框 ───────┤
     └─> vest (自训 yolov8n) ─> vest / no_vest 框 ──────────┴─> 规则引擎
```

为什么要拆：公开的安全帽权重**只有 Hardhat / NO-Hardhat 两类，没有 person**。  
判定链第一步要「谁在画面里」，单用一个模型时每张图都是 0 人。

| 权重 | 用途 | 来源 | 是否自训 |
| :--- | :--- | :--- | :---: |
| `yolov8n.pt` | 人体检测 | COCO 预训练（HF `kadirnar/yolov8n-v8.0`） | ❌ |
| `best.pt` | 安全帽检测 | HF `keremberke/yolov8s-hard-hat-detection` | ❌ |
| `vest.pt` | 反光背心检测 | 本项目在 Chapian train 100 张上微调（强增强，45 轮） | ✅ **唯一自训** |

> ⚠️ **答辩措辞**：不能说「我们训练了安全帽检测模型」。准确说法是
> 「我们用公开权重 + 自训的背心模型组成三模型串联，并自建 100 张测试集完成评测」。
> 三个权重各自的许可证与 SHA256 见 [`docs/模型卡片.md`](docs/模型卡片.md)。

| 模型原始类别                | 引擎类别       | 说明           |
| --------------------- | ---------- | ------------ |
| `Person`              | `person`   | 人体基准框        |
| `Hardhat` / `helmet`  | `helmet`   | 正向证据         |
| `NO-Hardhat` / `head` | `nohelmet` | **反向证据**，不丢弃 |
| `vest` / `no_vest`    | `vest` / `novest` | 背心正/反向证据 |
| 其他（`boots`/`gloves`/`goggles`） | 丢弃 | 数据集里有标注，**没有对应模型**，别在 PPT 上写成「四类检测」 |

### 4.1 版本选型（架构实测：CPU / 640 / 15 次中位数）

| 架构          | 参数量    | FLOPs    | CPU 延迟      | 说明                   |
| ----------- | ------ | -------- | ----------- | -------------------- |
| yolov8n     | 3.16M  | 8.9G     | 44.2 ms     | 现在的 person 模型        |
| yolov8s     | 11.17M | 28.8G    | 97.6 ms     | 现在的 helmet 模型（第三方权重） |
| **yolo11n** | 2.62M  | **6.6G** | **41.4 ms** | 同规模最省                |
| yolo11s     | 9.46M  | 21.7G    | 88.7 ms     | 重训首选                 |
| yolo12n     | 2.60M  | 6.7G     | 52.9 ms     | attention 在 CPU 上反而慢 |
| yolo12s     | 9.28M  | 21.7G    | 102.0 ms    | 同上                   |
| yolo26n     | 2.57M  | **6.1G** | 43.9 ms     | FLOPs 最低，CPU 没优势     |
| yolo26s     | 10.01M | 22.8G    | 92.8 ms     | 待观察                  |
| yolo26-p2   | 2.66M  | 9.5G     | 65.3 ms     | 小目标变体，+56% 算力        |

数据：`data/arch_bench.json`（随机权重，只比架构开销，不含精度）。

**结论：**

- **架构上 v11 更省。** 同规模少 26% FLOPs（8.9G → 6.6G）、CPU 延迟低 6%（44.2 → 41.4 ms）。但这是「重训时」的结论，不是「现在换」的理由——见 4.2。
- **YOLO12 不要选。** 参数量最小，但 CPU 上慢 28%——attention 模块在 CPU 上是负担，导出也麻烦。
- **YOLO26 先观察。** FLOPs 最低（6.1G），但 CPU 延迟与 11n 持平；它的收益（NMS-free、端到端导出）要上 GPU/TensorRT 才体现。
- **P2 变体留给小目标。** 安全帽确实小，但 P2 要多付 56% 算力，多路场景吃不消。

**但现在换不了。** 三个权重全是 v8 结构，换架构等于丢权重重新训——完整理由、代价清单和
「什么时候该换」写在下一节。

**上了 GPU 之后，选择面变宽了：**

| 场景                     | 建议                                        |
| ---------------------- | ----------------------------------------- |
| 单机 20 路以内（RTX 5060 够用） | 维持现有三模型（v8n + v8s + vest），≈22 ms/帧，25 路 |
| 路数多、想省显存（**需先重训**）     | **YOLO11n**，FLOPs 只有 s 的 1/3              |
| 小目标漏得多（安全帽）            | 试 **yolo26-p2**：多付 56% 算力，GPU 上仍能跑到 ~40 路 |
| 要端到端导出 TensorRT        | **YOLO26**：NMS-free，省掉后处理，GPU 上是纯赚        |

CPU 上的结论不变（重训时 v11 优先、v12 别碰）；GPU 上 YOLO26 才真正开始有优势。

### 4.2 为什么现在还是 YOLOv8，不是 YOLO11

一句话：**架构上 v11 更省，但本项目的三个权重都是 v8 结构——换架构等于连权重带阈值一起重来，
而这条路的收益是 6% 耗时、0 业务收益。** 四条理由，按硬度排。

**① 三个权重全是 v8，v11 加载不了。**

| 权重 | 结构 | 来源 |
| :--- | :--- | :--- |
| `yolov8n.pt` | YOLOv8n（COCO） | 第三方 |
| `best.pt` | **YOLOv8s** 安全帽微调 | 第三方 `keremberke/yolov8s-hard-hat-detection` |
| `vest.pt` | YOLOv8n 微调（自训） | 我们从 Chapian train 100 张微调 |

YOLO11 换了骨干（C3k2）与检测头，`.pt` 不跨版本兼容。换 = 三个模型全部重训或重找，
其中安全帽那个**没有公开的 v11 版本**可用——只能自己训，而我们的自采数据至今 0 张。

**② 重训这条路已经走过一次，同架构、更少变量，仍然输了。**（详见 5.4 / 5.5）

在 `helmet_p2` 的 1300 张上微调 v8s：helmet AP 0.5645 → **0.7376（+31%）**，业务指标却全面变差——

| | helmet AP | 误报 | 漏报 |
| :--- | ---: | ---: | ---: |
| 第三方权重（现用） | 0.5645 | **5.1%** | **24.7%** |
| 同架构微调 1300 张 | 0.7376 | 17.4% | 32.3% |

扫遍几何网格，原模型在**每一个工作点**都占优（漏报 24.7% 档：误报 5.1% vs 16.3%）。
根因不是模型差，是**框更紧**：帽框/头部区域 IoU 从 0.410 掉到 0.291、框面积比 0.86 → 0.60，
而阈值是照原模型的框几何标的。换成 v11，等于在这层之上再叠一层没测过的未知
（v11 的框回归风格、置信度分布）。

**③ 换架构的账单：四个指标 + 两套阈值 + 两条后端 + 全部文档。**

| 要重做的事 | 为什么 |
| :--- | :--- |
| 重测四个指标 | `data/metrics_*.json`、README、技术页、置信区间全部换数 |
| 重扫两套阈值 | `measured` 的 0.30 / 0.20 与 IoU 0.25 是在 **v8 的分数分布与框几何**上扫出来的 |
| 重验 ONNX 一致性 | `onnx_backend` 自己实现 letterbox / decode / NMS，默认 v8 的 `(1, 4+nc, N)` 输出头 |
| 重写文档 | 凡是引用 0.6808 / 5.1% / 22.58% / ≈22 ms 的地方，全部作废 |

换来的收益：arch bench 上同规模 CPU 41.4 vs 44.2 ms（**−6%**）、FLOPs 6.6G vs 8.9G（**−26%**）。
落到交付路径（三模型 ≈22 ms、25 路）上，就是从 25 路变 26 路——**业务上无感**。

**④ v11 的强项不在我们的瓶颈上。**

v11 主要赢在 COCO 通用 mAP 与参数效率；我们的瓶颈是 helmet 类 AP 0.5645（第三方权重上限）
叠加域偏移（全是境外工地图、自采 0 张），**不是骨干网络**。小目标漏检要靠 P2 头或提高输入分辨率，
代价是 +56% 算力（arch bench：65.3 vs 41.4 ms）——也不是换版本能解决的。

**那什么时候换？** 给三个触发条件，避免「永远不换」：

1. 自采数据到位（现在 0 张），且重训后业务指标能追平 5.1% / 22.58%；
2. 路数成为瓶颈（GPU 打满、要上 TensorRT），那时收益是吞吐而不是精度；
3. 真换的时候按「重训 → 重扫两套阈值 → 重测四指标 → 重验 ONNX 一致性」四步走，缺一步数字不可比。

**答辩话术**：v11 架构更省（同规模少 26% FLOPs），但三个权重都是 v8 结构，换架构要连权重带阈值
一起重来；我们在同架构上试过重训，AP 涨 31%、业务指标反而全面变差——所以现在选的是
「指标可信」而不是「版本最新」。重训窗口一开，就切 YOLO11。

## 五、指标（100 张真实照片实测）

> 现场要的是**实时监控视频巡查**，所以下面每个配置都同时看三件事：  
> 准不准（mAP/误报/漏报）、多快（单帧耗时）、**单进程能带几路摄像头**（按 1fps 抽帧、留 30% 余量）。
>
> **口径说明**：下面 mAP 是关闭人员门控时测的（0.688）。开启门控后 mAP 为 **0.681**，  
> 差异只来自「无人帧不再输出装备框」——业务三指标（误报/漏报/混淆矩阵）完全不变。  
> 交付用的 `data/metrics_real.json` 是开启门控的真实配置（0.681 / 5.1% / 22.58%）。

### 5.1 配置扫参（6 组，同一测试集，**耗时列为 CPU 实测**）

| 配置             | mAP@0.5   | helmet AP | 误报率       | 漏报率       | 单帧耗时        | 单进程可带   |
| -------------- | --------- | --------- | --------- | --------- | ----------- | ------- |
| s @480         | 0.685     | 0.562     | 15.8%     | **34.5%** | **89.5 ms** | **7 路** |
| **s @640**（默认） | **0.688** | **0.579** | **11.2%** | 38.7%     | 138 ms      | 5 路     |
| s @960         | 0.654     | 0.515     | 17.0%     | 45.2%     | 308 ms      | 2 路     |
| m @480         | 0.569     | 0.331     | 15.8%     | 37.9%     | 170 ms      | 4 路     |
| m @640         | 0.547     | 0.297     | 18.4%     | 38.7%     | 283 ms      | 2 路     |
| m @960         | 0.545     | 0.297     | 16.0%     | 40.9%     | 637 ms      | 1 路     |

**两个反直觉的结论，都实测过：**

1. **换更大的模型反而更差**（yolov8m 掉 14 个点）。因为 keremberke 的 m 版权重是在另一个版本的数据上训的，  
   类别口径和这批现场图对不上。**跨数据集的权重不能按模型大小挑，只能按实测挑。**
2. **提高分辨率也掉点**（960 掉 3.4 个点、慢 2.2 倍）。模型是在 640 上训练的，放大推理等于把目标推出训练分布。

→ **当前 s @640 已经是这批权重的最优点**。想要更高精度，只有一条路：用自己的数据微调（见第九节）。

要带更多路数就换 `--imgsz 480`：快 35%、能带 7 路，代价是误报从 11.2% 升到 15.8%、mAP 几乎不变。

### 5.2 四个指标的正式口径（s @640）

| 指标          | 初版      | **现行**        | 目标      | 判定       |
| ----------- | ------- | --------------------- | ------- | -------- |
| mAP@0.5     | 0.688   | **0.681**    | ≥ 0.85  | ❌        |
| 误报率         | 11.2%   | **5.1%**（↓6 个点）       | ≤ 10%   | ✅ **达标** |
| 漏报率         | 38.7%   | **22.6%**（↓16 个点）     | ≤ 5%    | ❌ 但在收敛   |
| 单帧耗时（GPU）   | 25.7 ms | **≈22 ms**（p95 ≈25） | ≤ 50 ms | ✅ **达标** |
| 单进程可带（1fps） | 25 路    | **25 路**              | —       | —        |

CPU 上是 138 ms / 5 路，GPU（RTX 5060）上 ≈22 ms / 25 路，**精度三项一字不差**——  
换设备只影响速度不影响判定，这本身就是可复现性的证据。  
（mAP 0.688→0.681 是开了人员门控：无人帧不再输出装备框，检测级指标略降，业务三指标不变。）

**100 张够不够？** 见 [`docs/指标置信区间.md`](docs/指标置信区间.md)（`tools/metric_ci.py` 生成）：

| 指标 | 点估计 | 95% 置信区间 | 目标 | 怎么表述 |
| :--- | ---: | :---: | ---: | :--- |
| 误报率 | 5.1%（5/98） | 2.2–11.4% | ≤10% | **点估计达标**，区间上界越线，不说「稳定达标」 |
| 漏报率 | 22.6%（21/93） | 15.3–32.1% | ≤5% | 区间下界仍超标 → 差距不是样本量造成的 |

颗粒度：误报率每 1 例 ≈ 1.02 个百分点。100 张能分辨「差一个量级」，分辨不了「差一两个点」。

**漏报率的分母是谁？** 22.6% 是 21/93，统计的是**已检出的人**——没被检测到的人不进分母。
同一批数据换整条链路口径（`--metric-scope e2e`，未检出的人算漏报）重算：

| 口径 | 合规人次 | 违规人次 | 误报率 | 漏报率 |
| :--- | ---: | ---: | ---: | ---: |
| `matched`（默认，衡量判定层） | 98 | 93 | 5.10% | 22.58% |
| `e2e`（衡量整条链路） | 107 | 105 | 4.67% | **31.43%** |

真值可判 212 人次，实际进统计 191 人次（覆盖率 90.1%），差额就是检测层没匹配上的人。
两个口径 `evaluate_real.py` 都会算，headline 用哪个由 `--metric-scope` 决定。
（仓库里那份 `metrics_real.json` 是加这个字段之前跑的，四个 headline 数字逐位不变；
重跑一次即带 `scope_detail` 与 `coverage`。）

答辩措辞：说 22.6% 时必须带一句「已检出人员口径」，否则等于把检测漏检藏起来了。

**换个分辨率还准不准？** 同一批 100 张 3 倍上采样到 1920×1920 再跑一遍（`data/metrics_1080.json`）：
mAP **0.6829**、误报 **5.10% 一例没涨**、漏报 **24.73%**（+2.15 点）、单帧 **44.8 ms**（p95 54.1）。
误报不动说明判定链对分辨率不敏感；漏报的小幅上涨来自上采样插值失真，不是阈值问题。
⚠️ 这是上采样素材，不是真实摄像头录像，只能证明「分辨率变化下的稳健性」。详见 [`docs/技术口径.md`](docs/技术口径.md) 4.1。

**漏报 21 例逐条归因：**

| 去向               | 例数 | 占比  | 性质       |
| ---------------- | -- | --- | -------- |
| 模型真的看错（裸头被框成安全帽）   | 15 | 71% | 只能靠更好的权重 |
| 目标过小 / 半身判「无法判定」      | 4  | 19% | 设计取舍     |
| 灰区待复核（0.20–0.30） | 2  | 10% | 保护机制在工作  |

**调参已经到头了。** 剩下 21 例漏报里 71% 是模型真的看错，阈值再动也救不回来——  
这部分只能靠更好的权重，而权重受限于公开数据与国内现场的域差。

### 5.3 六步优化（每一步都先测后改）

| # | 改动                                                 | 漏报                | 误报                   | 依据                                                       |
| - | -------------------------------------------------- | ----------------- | -------------------- | -------------------------------------------------------- |
| — | 初版                                                 | 38.7%             | 11.2%                | —                                                        |
| ① | 面积阈值按画面占比换算                                        | 45.2% → 38.7%     | 11.2%                | `8000px²@1080p` = 画面 0.386%；原来拿绝对值套 640×640，小目标整片判「无法判定」 |
| ② | 裸头框作反向证据                                           | 38.7% → 38.7%     | 11.2%                | 有帽框算戴、裸头框算没戴、两者都有转人工                                     |
| ③ | CONF_FINAL 0.60 → 0.40                             | 38.7% → 23.7%     | 11.2%（未升）            | 扫 8 档阈值                                                  |
| ④ | **HELMET_IOU_MIN 0.30 → 0.25** + CONF_FINAL → 0.30 | **23.7% → 24.7%** | **11.2% → 7.1%（达标）** | CF × IOU 二维网格，见 `data/sweep_rules.json`                  |
| ⑤ | **MAX_EQUIP_RATIO 1.60 → 3.00** | 24.7%（不变） | **7.1% → 5.1%** | 几何阈值扫参，见 `data/sweep_geom.json`                        |
| ⑥ | **MIN_ASPECT 1.20 → 0.90** | **24.7% → 22.6%** | 5.1%（不变） | 4 例高宽比告警逐例看：蹲姿 2 例头部仍在「顶部 30%」内，弯腰/侧躺 2 例继续判「无法判定」 |

第 ③ 步是这次最值钱的发现：**误报完全不随 CONF_FINAL 变化**。  
原因是 FP 全部来自「高置信度、确实没帽框」的误判，而漏报里有一大批是  
「人框置信度中等、没检出帽框」——原来被判「转人工」，阈值一降就变成「确认违规」。  
扫到 0.40 是拐点，再往下（0.25–0.35）结果完全一致。

第 ④ 步是一次**交换**而不是净赚：漏报涨了 1 个点，换来误报从 11.2% 降到 7.1%（首次达 ≤10% 目标）。  
判断依据是**稳定性**——把测试集对半切开分别评：

| 配置                        | A 半（50 张）误报 | B 半（50 张）误报 |
| ------------------------- | ----------- | ----------- |
| 旧（CF 0.40 / IOU 0.30）     | 8.5%        | 15.4%       |
| **新（CF 0.30 / IOU 0.25）** | **6.8%**    | **7.7%**    |

旧配置在两半上波动 7 个点，新配置只波动 1 个点——**低而且稳**，这才是选它的理由。

第 ⑥ 步的口径：`MIN_ASPECT` 原本防的是「头部已不在人体框上部」，一旦放宽，弯腰作业就有拿后背当头部的风险。
所以不是拍脑袋放，是把 4 例触发它的样本逐张看过——蹲姿那两例头部确实落在判定区内，判「无法判定」等于白丢告警；
高宽比 0.80 / 0.71 的两例（弯腰、侧躺）头部已经偏出区域，继续留作「无法判定」。**放宽到 0.90，误报一例没涨。**

> ⚠️ 本节与 5.4–5.8 的对照表都是**在当时配置下**测的历史数据（`MIN_ASPECT=1.2`），
> 只用于横向比较；绝对值与当前口径差 2.15 个百分点，别混着引用。

> ⚠️ 阈值仍是在测试集上选的，属乐观估计。**换模型后必须用 `sweep_rules.py` + `sweep_geom.py` 各扫一遍。**  
> 另外 CONF_REVIEW 降到 0.20 后，「丢弃」这一档实际已不可达（低于检测 conf 0.25 的框根本不会输出），  
> 三档保护在 helmet 上退化成「定论 / 待复核」两档。这一点如实写在代码注释里。

### 5.4 微调实验：两轮，AP 都涨了，业务指标都跌了

第一轮（80 张）以为是数据不够，于是扩了数据源再训一轮。

**第二轮数据**：新增 `toborobot/Safety-helmet-dataset`（MIT，4916 训练 / 1413 验证 / 706 测试），
人工抽样核对过类别：**0 = 没戴帽，1 = 戴了安全帽**（裁框放大看图确认，不是猜的）。
与原数据混训：**1300 张 / 5235 框**，其中同域的 Chapian 100 张用来把域拉住。

| | helmet AP | mAP@0.5 | 误报 | 漏报 |
|---|---|---|---|---|
| 第三方权重（现用） | 0.5645 | 0.681 | **5.1%** | **24.7%** |
| 微调 80 张 | 0.766 | 0.781 | 18.4% | 34.4% |
| 微调 1300 张 | **0.7376**（+31%） | **0.767** | 17.4% | 32.3% |

训练域上第二轮很强（自己的验证集 mAP50 **0.935**，helmet 0.96），但换到我们的测试集，业务指标仍然全面变差。

**阈值重扫救不回来。** 换了模型就必须重扫两套阈值——置信度阈值和几何阈值：

```
python src/anxun/sweep_rules.py --ppe runs/ft_mix/weights/best.pt   # 置信度
python src/anxun/sweep_geom.py  --ppe runs/ft_mix/weights/best.pt   # 几何
```

同一套几何网格（`data/sweep_geom.json`）下，两个模型的帕累托前沿：

| 漏报水平 | 原模型误报 | 微调模型误报 |
|---|---|---|
| ~24.7% | **5.1%** | 16.3% |
| ~18.3% | **12.2%** | 55.1% |

**原模型在每个工作点都占优**，微调模型没有任何一组阈值能追平。

### 5.5 为什么 AP 涨了 31% 业务反而差：框的几何变了

这是本轮最值得记的发现。直接量「帽框和头部区域的吻合程度」：

| | GT 帽框找到率 | 帽框 vs 头部区域 IoU | IoU≥0.25 占比 | 框面积/区域面积 | 置信度 |
|---|---|---|---|---|---|
| 原权重 | 84% | **0.410** | **80%** | 0.86 | 0.595 |
| 微调 | **86%** | 0.291 | 52% | **0.60** | **0.742** |

微调模型**看得更准、置信度更高、召回也略高**——但**框画得更紧**（面积只有头部区域的 0.60 倍）。
框一小，和头部区域的 IoU 就从 0.410 掉到 0.291，而判定阈值 `HELMET_IOU_MIN=0.25` 是照旧模型的框几何调出来的。

更麻烦的是**小框在「包含度」判据下反而占优**（包含度 = 交集/框面积，框越小越容易高），
于是裸头上一个小的误检框就能通过 `CONTAIN_MIN`，把没戴帽的人判成戴了——这同时推高了误报和漏报。

**结论：模型换代的成本不只是重训，还有整套判定阈值的重新标定。**
AP 这类检测级指标和业务指标之间隔着一层「框几何 + 置信度校准」，不能只凭 AP 选模型。

### 5.6 扫参的副产品：误报 7.1% → 5.1%

`MAX_EQUIP_RATIO`（装备框面积不得超过头部区域的倍数）原来是 1.60。
扫参发现原模型的帽框面积分布右尾能到 2 倍以上，1.60 的上限会把一批**真的戴了帽**的正确框整条拒掉，
于是合规的人被判未佩戴。放宽到 3.00：

| 配置 | 误报 | 漏报 | FP | FN |
|---|---|---|---|---|
| IOU 0.25 / CONTAIN 0.60 / MAXR 1.60 | 7.1% | 24.7% | 7 | 23 |
| **IOU 0.25 / CONTAIN 0.60 / MAXR 3.00** | **5.1%** | **24.7%** | **5** | **23** |

这个修复在图上是可验证的：`R-01` 那张演示图原本被报成「未佩戴安全帽」，
放宽阈值后翻转成「已佩戴」。那张图没有标注（GT 是空的），所以我直接看了原图——
**人头上戴的是黄色安全帽**，之前的告警是误报。这也说明当初按模型自己的输出挑演示场景是循环论证，
以后挑场景必须先看有没有标注。

### 5.7 补上 vest：让「未穿戴反光背心」这条判定真正跑起来

规则引擎一直支持 vest（上身区域判定 + L/S 风险矩阵 + 整改动作），但**从来没有对应权重**，
所以这条判定实际是空转的。本轮补上。

数据只有 Chapian 的 100 张 train（75 个 vest + 237 个 no_vest）。反光背心是大目标、
特征强，这个量级勉强够用——和安全帽那种 30px 小目标不是一回事。

**训练过程踩了一个值得记的坑**：第一版 `data.yaml` 里 `val` 和 `train` 是同一批图，
模型选择等于在训练集上做。结果训练集 mAP50 **0.995**，看着很美，换到独立测试集只剩 **0.415**。
改成 80/20 真切分后，验证集 mAP50 只有 0.377——**小验证集上的模型选择噪声极大**，
方法正确不代表结果更好。最后按标准做法：用 80/20 实验定轮数（38 轮，曲线仍在涨），
再在全量 100 张上重训 45 轮。

**独立测试集成绩**（100 张全程未参与训练与选轮次）：

| | mAP@0.5 | 误报率 | 漏报率 |
|---|---|---|---|
| vest | 0.4401 | — | — |
| no_vest | 0.4646 | — | — |
| **业务指标** | — | **27.3%**（44 合规人次） | **13.0%**（185 违规人次） |

误报 25% 不好看，但是诚实的：100 张训练数据就这个水位。vest 现在**能用**，
但离 helmet 的 5.1% 还差得远，瓶颈同样是数据。

**接入成本几乎为零**：GPU 上三模型 7.1 ms vs 双模型 6.9 ms，只多 **0.2 ms**
（vest 是 yolov8n 量级，GPU 本来就没吃满）。ONNX 路径同样支持，两个后端输出逐框一致。

**顺带修了两个真 bug**：

1. `detectors.LABEL_MAP` 把 `no_vest` 放在了 `IGNORE` 里——vest 模型的一半输出
   （没穿背心）被静默丢弃，只剩「穿了」一类，业务指标全是 None。
2. `evaluate_real.GT_MAP` 里没有 vest 两类，真值被整类丢掉，统计出来 0 合规 / 0 违规。
   两个 bug 都是静默的，不报错，只是数字变空。

 helmet 指标**完全不受影响**（加 vest 前后都是 0.6808 / 5.1% / 22.58% / 72-21-5-93），
这一点是显式验证过的，不是推的：`--vest` 原先是个只声明、没接线的空参数，
v1.2.0 修补时接上了，现在一条命令即可复现（代价是单帧 ≈22 → ≈32 ms，三个模型）：

```bash
python tools/make_vest.py                                    # 建 80/20 数据集
python src/anxun/finetune.py --data datasets/vest/data.yaml \
    --init models/yolov8n.pt --name vest_ft                  # 定轮数
python src/anxun/evaluate_vest.py                            # 独立测试集评测
python src/anxun/evaluate_real.py --vest models/vest.pt      # 加背心后 helmet 四项应逐位不变
```

### 5.8 按装备分离阈值：helmet 和 vest 不能用同一套

vest 接入后暴露出一个结构问题：**helmet 和 vest 共用一套几何阈值**，但两者的判定区域
完全不同（头部 vs 上身），框的几何分布也不一样，共用必然有一个吃亏。

扫验证实了这一点：

| 装备 | 最优 IOU_MIN | 最优 MAX_EQUIP_RATIO | 误报 | 漏报 |
|---|---|---|---|---|
| helmet | **0.25** | **3.0** | 5.1% | 24.7% |
| vest | **0.10** | **6.0** | 27.3% | 13.0% |

如果把 helmet 也降到 IOU 0.10，它的误报会从 5.1% 抬到 **9.2%**；反过来 vest 用 0.25
则匹配不上（vest 模型把背心框画得偏松，相对上身区域偏小）。**两个装备的最优点不在同一个位置**，
只能分开。

实现（`rules_engine.equip_cfg`）：

```python
EQUIP_OVERRIDE = {
    "vest": {"iou_min": 0.10, "contain_min": 0.60, "max_ratio": 6.0},
}
```

helmet 继续用模块常量（`sweep_rules.py` / `sweep_geom.py` 直接改它们，是 helmet 的扫参入口），
其他装备在这里覆盖，没有覆盖的退回模块常量。这样改**不需要动扫参脚本**。

验证：分离后 helmet 四项完全不变（0.6808 / 5.1% / 22.58% / 72-21-5-93），
vest 从误报 31.8% / 漏报 11.4% 变为 **27.3% / 13.0%**——和扫参预测的 27.3/13.0 一字不差。

### 5.9 重增强：没有更多数据时怎么抗过拟合

vest 第一版训练集 mAP 0.995 / 测试集 0.415，典型过拟合。没有新数据可用
（HF 镜像上 6 个候选 vest 仓库全是空的），只能从增强入手：

| 配置 | 验证集 mAP50 | 测试集 mAP50 | 误报 | 漏报 |
|---|---|---|---|---|
| 普通增强（80 张） | 0.377 | 0.415 | 25.0% | 17.3% |
| **重增强**（80 张） | **0.734** | 0.450 | 34.1% | 14.1% |
| 重增强 + 全量 100 张 | — | **0.452** | 31.8% | 11.4% |

重增强把验证集 mAP 从 0.377 拉到 0.734（接近翻倍），`--aug strong`：
mosaic 1.0、scale 0.5、mixup 0.1、copy_paste 0.1、weight_decay 0.001、加 shear/perspective。
代价是误报上升，最后靠 5.9 的分离阈值把误报压回 27.3%。

⚠️ 注意验证集只有 20 张，0.734 这个数本身不可靠（测试集只到 0.452）——
它只够用来比较「强增强 vs 普通增强」的相对优劣，不能当成绩报。

## 六、视频巡查（实时监控）

```bash
# 单路
python src/anxun/stream.py --source rtsp://10.0.0.8/stream1 --fps 2 --region B-01
# 多路（批处理调度）
python src/anxun/scheduler.py --sources rtsp://cam1,rtsp://cam2,cam3.mp4 --fps 1 --batch 4
```

链路：三级触发 → 批处理推理 → 双模型检测 → 四态判定 → 跨帧跟踪 → 3 帧定论 → 事件去重。

### 6.1 三级触发：先决定哪些帧值得算

固定机位的大部分时间是空画面。真正的浪费不是模型慢，是**算了不需要算的帧**。

| 级      | 判据           | 省掉什么           | 实测（`datasets/site_demo.mp4`：60s / 600 帧 / 占用率 15%） |
| ------ | ------------ | -------------- | -------------------------------------------------- |
| ① 抽帧   | 2fps         | 25fps 里 96% 的帧 | 600 帧 → 120 次采样                                    |
| ② 帧差   | 灰度均差 < 10.0  | 静止画面的整帧推理      | 120 → **21 次**推理（-82.5%）                           |
| ③ 人员门控 | 画面里没有 person | PPE 模型的整次前向    | 采样帧中 103/120 无人，**省 86% 的 PPE 前向**                 |

三级叠加：**240 次前向 → 39 次（-84%）**，告警结果与全量推理完全一致（1 条，同一时刻同一人）。

### 6.1.1 1080p 真实素材复验：阈值 3.0 在现场会失效

上面那组数字来自 **640×640 合成动画**。真实部署是 1080p 摄像头，于是用
`datasets/ppe_test/test1080`（100 张 1920×1920 真实照片，3 倍上采样，YOLO 标注随行）
串了两段监控流复验：**纯静态切换** 与 **±1.5px 机位抖动**（真实固定机位必然有轻微晃动），
每张画面停留 5 秒，共 100 秒 / 2500 帧。复验脚本 `tools/verify_trigger_1080.py`。

| 版本 | 帧差中位数 | 阈值 3.0 跳过 | 前向节省 | 告警 vs 全量 |
|---|---|---|---|---|
| 纯静态 | 0.0 | 90.9% | 省 90% | 45 vs 45 ✅ |
| **±1.5px 抖动** | **3.862** | **33.2%** | **只省 39%** | 51 vs 49 ✅ |

**结论：机位晃动本身就能把帧差推到 3.86，超过原阈值 3.0**——触发层的帧差判据在现场会
直接失效，节省从 90% 掉到 39%。这不是理论风险，是实测。

于是扫了一遍阈值（同一全量基准，判据是告警一条不漏）：

| 帧差阈值 | 抖动版前向节省 | 告警一致性 |
|---|---|---|
| 3.0（原值） | 39% | ✅ |
| 6.0 | 76% | ✅ |
| **10.0（现值）** | **86%** | ✅ |
| 15.0 / 25.0 | 90% | ✅ |

**默认阈值已改为 10.0**（`stream.py` / `scheduler.py` 同步）。取 10.0 而不是更极端的 25.0，
是因为要为「人缓慢走近」留余量：场景切换的帧差是 88+，人走动的帧差远大于机位晃动的 3.86，
10.0 距离两者都有充足间隔；再往上就是在赌现场没有缓慢移动的目标。

⚠️ **这条复验的边界必须说清**：素材是静态照片，**没有真实人体运动**。
「人走动会产生远大于 10 的帧差」是推断，不是实测。上现场前应拿一段真人走动的录像
复核阈值上限——触发层省得越多，漏看的风险也越大，这个方向的风险还没被证伪。

人员门控在语义上**完全无损**：判定是「按人」做的，画面里没有 person 时装备框不参与任何判定。  
代价只体现在检测级 mAP 上（0.688 → 0.681）——无人帧不再输出装备框，而 mAP 会把那些帽子算成漏检。  
**业务指标一个数没变**：误报 5.1%、漏报 22.58%、混淆矩阵 72/21/5/93 完全一致。

⚠️ 帧差跳帧踩过一个坑：一开始「跳过」等于整帧丢弃，画面不动时三帧永远凑不齐，一条告警都出不来。  
正确做法是**跳过推理但复用上一帧的检测结果**继续推进时序窗口——人站着不动，也得能判出他没戴帽。


### 6.2 批处理调度：把「一路一帧」改成「多路一批」

原来每路各跑各的，GPU 一次只算一张图。改成锁步攒批后：

| batch | 总耗时 | 每帧 | 相对 |
|---|---|---|---|
| 1 | 19.5 ms | 19.5 ms | 1.00× |
| 2 | 30.3 ms | 15.2 ms | 1.29× |
| **4** | **54.8 ms** | **13.7 ms** | **1.40×** |
| 8 | 118.0 ms | 14.8 ms | 1.32× |
| 16 | 224.9 ms | 14.1 ms | 1.39× |

**batch=4 是这块卡的最优点，再大没有收益。** 瓶颈不在 GPU 算力，而在 CPU 侧的预处理
（letterbox）与后处理（NMS）——这部分不随批大小摊薄。所以「堆批大小」这条路到这里为止，
真正的杠杆是 6.1 的触发层。

数据：`data/batch_bench.json`。

### 6.3 判定与推理解耦

`scheduler.py` 把链路拆成三段，每段职责单一：

```
读取（每路独立：抽帧/帧差）  →  推理（共享 GPU：攒批前向）  →  判定（每路独立：StreamPipeline）
```

- 推理层只认「N 帧进、N 组框出」，不知道什么叫违规；
- 判定层只吃「框 + 时间戳」，不知道底下是 GPU 还是 CPU、批多大。

所以单路 `stream.py` 和多路 `scheduler.py` 复用**同一份** `StreamPipeline`，
同样的输入必定得到同样的事件——这是能对账的前提。

> 用锁步（lockstep）而不是异步队列，是为了可复现。真上现场只需把 `next_sample()`
> 换成带超时的队列，判定层一行不用改。

容量分两种情况，别混：

- **640 输入**（抽帧后缩放，线上默认）：单帧 6.9 ms（双模型）/ 7.1 ms（三模型），GPU 远未吃满。
- **1080p 原生输入**（1920×1920，1080p 复验实测）：单帧 **30.5 ms**——letterbox 从大图缩到 640
  的开销 + 更多候选框，比 640 输入慢 4 倍多。这是真实部署要按的数。

三级触发层在 1080p 上省 84~90% 的前向（见 6.1.1），综合下来单进程仍可带 20 路以上。
综合下来**单进程约 25 路 @2fps，或 50 路 @1fps**；CPU 模式只剩 5 路。

> **触发层的副作用（值得提前知道）**：4 路 × 60s 实测，推理只用了 80 次、实耗 6.25s，
> 但墙钟时间并不是推理决定的——2400 帧的解码（`cv2.read`）成了新瓶颈。
> 也就是说：**推理优化到一定程度后，瓶颈会从 GPU 转移到视频解码**。
> 下一步该做的是接 RTSP 时用硬件解码 / 只解关键帧，而不是继续优化模型。

### 6.4 两个被否掉的架构方案（实测数据在此）

做架构升级时试过两条路，都失败了。留在这里，省得以后有人再试一遍：

| 方案 | 想法 | 实测 | 为什么失败 |
|---|---|---|---|
| **级联 ROI 精查** | 全图找到人，把头部裁出来放大再跑一次 PPE | 640 原生集漏报 24.7% → **30.1%**；1080p 模拟集仅 26.9% → 25.8% | 裁出来放大等于把目标推出训练分布——模型没在「一个大头」上训过，开始幻觉出帽子 |
| **双模型 WBF 融合** | 原权重 + 微调权重各出框，加权融合 | 漏报 24.7% → **33.3%**，误报不变 | 微调权重会凭空看出帽子，融合把它的错也一起采信，违规被判成合规 |

结论：**在权重与场景不匹配的前提下，加架构只会放大错误，不会纠正错误。**
准确度的天花板在权重，不在结构。

> 这两个方案的实验代码已从交付仓库移除（属于过程产物），实测数字保留上表，
> 因为它们是「为什么不往架构上继续投入」的直接依据。
