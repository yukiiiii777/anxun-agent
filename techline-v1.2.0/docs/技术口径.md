## 一、判定阈值：只有一套定义，两个口径

阈值定义在 **`config/thresholds.json`**，`rules_engine.py` 启动时加载，
`/api/scenes`、评测 JSON、验收脚本都从这里取数。**代码里不再写死任何阈值。**

| 参数 | `measured`（默认） | `conservative` | 含义 |
| :--- | ---: | ---: | :--- |
| `conf_final` | **0.30** | 0.60 | ≥ 此值直接下结论 |
| `conf_review` | **0.20** | 0.40 | 低于此值丢弃；两值之间转人工复核 |
| `helmet.iou_min` | **0.25** | 0.30 | 安全帽框与头部区域的 IoU 下限 |
| `helmet.contain_min` | 0.60 | 0.60 | 包含度下限（小目标的并列判据） |
| `helmet.max_ratio` | **3.00** | 3.00 | 装备框面积 ≤ 区域面积的倍数 |
| `vest.iou_min` | **0.10** | 0.30 | 背心框与上身区域的 IoU 下限 |
| `vest.max_ratio` | 6.00 | 6.00 | 同上 |
| `head_region_ratio` | 0.30 | 0.30 | 头部区域 = 人员框上部 30% |
| `head_width_ratio` | 0.44 | 0.44 | 横向取中间 44%（头宽 ≈ 0.44 肩宽） |
| `min_person_area` | 8000 px² | 8000 px² | 1920×1080 下标定，运行时按画面占比换算 |
| `min_aspect` | 0.90 | 0.90 | 人员框高宽比下限（半身/蹲姿不判） |

### 用哪一套

| 场景 | 口径 | 理由 |
| :--- | :--- | :--- |
| **交付数字、答辩、`evaluate_real.py`** | `measured` | 0.6808 / 5.10% / 22.58% / ≈22 ms 就是它跑的；评委当场重跑必须得到同一组数 |
| 控台演示、录屏、想让「待复核」这一档出现 | `conservative` | 置信度 0.52 这类样本会落进灰区，四态齐全，能看见保护机制 |
| 阈值扫参 | 直接改模块常量 | `sweep_rules.py` / `sweep_geom.py` 的既有行为，扫完自己还原 |

> **规矩：一个作品不能有两套判定标准。** 演示用 `conservative` 时，
> 录屏、PPT、口播必须写明「演示用保守配置 0.60/0.40，实测配置 0.30/0.20」，
> 不能只写「我们的阈值是 0.6」——那是把演示口径冒充成评测口径。

### 误报 / 漏报按谁统计

同一个 `measured` 口径下，误报漏报还有一层分母选择，两个都要会答：

| `--metric-scope` | 统计范围 | 误报率 | 漏报率 | 回答什么问题 |
| :--- | :--- | ---: | ---: | :--- |
| `matched`（默认，headline） | 只算**已检出的人** | 5.10%（5/98） | 22.58%（21/93） | 判定层判得准不准 |
| `e2e` | 连没检出的人一起算 | 4.67%（5/107） | **31.43%**（33/105） | 整条链路一共漏了多少 |

真值可判 212 人次，实际进统计 191 人次（覆盖率 90.1%），差额就是检测层没匹配上的人。
`evaluate_real.py` 两个口径都会算并写进 JSON（`scope_detail` / `coverage`），
`--metric-scope` 只决定 headline 用哪个。

> 说 22.58% 时必须带一句「已检出人员口径」，否则等于把检测漏检从分母里藏起来了。

### 怎么切

```bash
# 环境变量（整台机器生效）
ANXUN_RULES_PROFILE=conservative python src/anxun/app.py

# 命令行（单次生效，app.py / evaluate_real.py 已接）
python src/anxun/app.py --profile conservative
python src/anxun/evaluate_real.py --profile conservative   # 只用于对比，别拿去报数
```

```python
from anxun import rules_engine as R
R.apply_profile("conservative")     # 代码内切换
R.profile_snapshot()                # 当前生效的整套阈值
```

### 换模型之后必须做的事

1. `python src/anxun/sweep_rules.py --ppe <新权重>`（置信度）
2. `python src/anxun/sweep_geom.py --ppe <新权重>`（几何）
3. 把扫出来的值写进 `config/thresholds.json` 的 `measured`，**不要只改代码**
4. 重跑 `evaluate_real.py`，更新 `data/metrics_*.json`
5. 同步本文第一节、README 第五节、技术页 P11；跑 `verify_all.py` 会拦住漏改

> ⚠️ 现有阈值都是在 100 张测试集上扫出来的，属**乐观估计**。
> 自采数据到位后必须复核，这是「指标好看」与「指标可信」的分界线。

## 二、类别体系：三层，别混着说

数据集有 9 类标注，但**只有 3 个模型、4 个引擎类别**。PPT 上写「四类检测」是错的。

| 数据集标注（9 类） | 模型输出 | 引擎类别 | 用途 |
| :--- | :--- | :--- | :--- |
| `person` | `person`（yolov8n / COCO） | `person` | 人体基准框，所有判定的锚点 |
| `hardhat` | `Hardhat`（best.pt） | `helmet` | 正向证据：戴了 |
| `no_hardhat` | `NO-Hardhat`（best.pt） | `nohelmet` | **反向证据**：没戴（不丢弃） |
| `vest` | `vest`（vest.pt） | `vest` | 正向证据：穿了 |
| `no_vest` | `no_vest`（vest.pt） | `novest` | **反向证据**：没穿 |
| `boots` / `no_boots` | — | 丢弃 | 有标注，**无模型** |
| `gloves` / `no_gloves` | — | 丢弃 | 有标注，**无模型** |

三个必须讲清的点：

1. **`goggles` 从来没做过。** `rules_engine.py` 里有 goggles 的判定分支与法规依据，
   但没有对应权重，`S_MAP` 里那两行是留给后续的。规划文档 `ppe.yaml` 写「4 类」是旧口径，
   以本表为准。
2. **`no_hardhat` / `no_vest` 不丢弃。** 它们是反向证据：正向框与反向框同时高置信时转人工，
   这是漏报率从 45% 降下来的关键改动之一。
3. **不同数据集的类名写法不一样**（`hardhat` / `Hardhat` / `hard hat` / `NO-Hardhat`），
   统一在 `detectors.YoloDetector.LABEL_MAP` 里映射；未映射的类名会进 `unmapped` 列表，
   验收时可查。训练集的 `data.yaml` 用的是相对路径，换机器不用改。

## 三、耗时口径：一个数，四个条件

**单帧耗时 = `evaluate_real.py` 在 100 张测试集上的均值（含前后处理）。**
离开这四个条件（imgsz 640 / conf 0.25 / 同一后端 / 同一机器），数字不可比。

| 路径 | 设备 | 单帧均值 | p95 | 出处 | 用途 |
| :--- | :--- | ---: | ---: | :--- | :--- |
| torch + CUDA | RTX 5060 Laptop | **≈22 ms** | ≈25 ms | `data/metrics_real.json` | 交付口径（GPU） |
| ONNX + CPU | 24 核 CPU | **72.7 ms** | 82.4 ms | `data/metrics_onnx.json` | 交付口径（无显卡） |
| torch + CUDA（三模型） | 同上 | 32.0 ms | 36.3 ms | `data/metrics_vest.json` | 加了背心模型的代价 |

> GPU 这条路三次复跑是 21.8 / 22.4 / 22.1 ms（p95 24.4–25.0），差值来自 GPU 时钟与后台负载，
> 不是代码变了。所以表里写 **≈22** 而不是小数：任何一次复跑都会落在 21–23 之间，
> 精确值以 JSON 里的 `latency.mean_ms` 为准。CPU 那条路径抖动小，保留 72.7 的原值。

**三个不算指标的数，别混进来：**

| 数 | 是什么 | 为什么不能用 |
| :--- | :--- | :--- |
| 8.8 / 31.7 ms | 启动自检的单帧探测 | 单帧单次，只证明「真的在用 GPU」，不是统计口径 |
| 6.9 / 7.1 ms | 多路批处理下的每帧成本（`batch_bench`） | 锁步攒批的场景，与单张评测不可比 |
| **53.5 ms（作废）** | v1.1.0 之前 ONNX-CPU 的旧数 | 出自未锁版本的 `onnxruntime`（`>=1.17`）。锁到 1.31.1 后同一模型复测 72.7 ms，两者不是同一环境 |

> 依赖版本已锁死在 `requirements-cpu.txt` / `requirements-gpu.txt`。
> **改版本 = 重跑 ONNX 评测 + 更新本表**，否则 53.5 → 72.7 这种 40% 的漂移会再来一次。

### 3.1 还有没有优化空间：有结论，不是感觉

被问「还能不能更快」时，答案是：**这套模型在这个 CPU 上已经到底了。** 依据是做过的三段剖析。

**① 耗时花在哪**（ONNX-CPU，20 张真实图，逐段计时）：

| 模型 | 合计 | 预处理（letterbox+归一化） | **前向** | 后处理（解码+NMS） |
| :--- | ---: | ---: | ---: | ---: |
| person（yolov8n） | 21.3 ms | 3.7 | **16.3** | 1.3 |
| ppe（yolov8s） | 33.5 ms | 3.6 | **29.5** | 0.4 |

前向占 **84%**，后处理不到 1 ms。也就是说：优化 NMS、优化 letterbox、换更快的解码写法，
最多省 2~3 ms，不值得动。

**② 线程数扫过了**（同一批图，两个 session 交替跑）：

| 线程数 | 1 | 2 | 4 | 6 | 8 | 12 | 24 | 默认（全核） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 单帧 | 349 | 209 | 122 | 92 | 77 | 71 | 64 | **57.5** |

默认全核最快，限线程只会更慢——CPU 侧是算力受限，不是调度受限。
（对比一下：`allow_spinning=0` 那一行的收益是 888 → 49 ms，那才是调度问题。）

**③ 剩下三条路，都要拿精度换**：

| 做法 | 能省 | 代价 |
| :--- | ---: | :--- |
| 降 `imgsz` 640 → 480 | ~35% | 误报 5.1% → 15.8%（540 节实测），业务上不可接受 |
| 换更小的权重 | 更多 | 精度直接掉，且第三方权重没有更小的高质量版本 |
| INT8 量化 | ~50% | 需要校准集，精度掉多少未知，测一次要重跑全部指标 |

**结论**：当前的 ≈22 ms（GPU）/ 72.7 ms（CPU）就是这套权重的下限。
真要更快，方向不是优化代码，是换更轻的模型 + 接受精度损失——那是产品决策，不是工程优化。

## 四、评测口径：四个指标怎么算的

| 指标 | 定义 | 分母 | 目标 |
| :--- | :--- | :--- | ---: |
| mAP@0.5 | 逐类 AP 的平均，IoU 0.5 | person 295 + helmet 146 个 GT 框 | ≥ 0.85 |
| 误报率 | 合规的人被判违规 | 98 个合规**人次** | ≤ 10% |
| 漏报率 | 违规的人被判合规 | 93 个违规**人次** | ≤ 5% |
| 单帧耗时 | 见第三节 | 100 张 | ≤ 50 ms |

**三条容易被追问的细节，先答上来：**

1. **按人次统计，不按图。** 一张图里有 3 个人就是 3 个样本，所以分母是 98/93 而不是 100。
2. **真值由标注推导，判定由引擎给出，两者不共享规则。** 硬帽框落在头部区域=合规，
   只检出 `no_hardhat`=违规，两者都无则跳过。这是「不自己跟自己比」的前提。
3. **测试集 100 张全程不参与训练与选轮次。** 微调实验用的是另一批数据（见 README 5.4）。

**未达标怎么办**：照实写，不写「达标」。四个指标里只有误报率与 GPU 耗时达标，
而且误报率的 95% 置信区间上界是 11.4%，越过了 10% 目标——所以准确表述是
「**点估计达标**」而不是「稳定达标」。区间与答辩话术见
[`指标置信区间.md`](指标置信区间.md)（由 `tools/metric_ci.py` 自动生成）。

### 4.1 第二个测试集：1080p 难例（分辨率稳健性）

主测试集 100 张是 640×640 左右的现场照。为了回答「换成分辨率更高的摄像头，判定还准不准」，
把同一批 100 张图**3 倍上采样到 1920×1920**（`datasets/ppe_test/test1080/`，标注随行），
用同一套权重、同一套 `measured` 阈值重跑一遍：

| 指标 | 主测试集（原生） | 1080p 难例集 | 变化 |
| :--- | ---: | ---: | :--- |
| mAP@0.5 | 0.6808 | **0.6829** | +0.002 |
| 误报率 | 5.10% | **5.10%** | 不变 |
| 漏报率 | 22.58% | **24.73%** | **+2.15 点** |
| 单帧耗时（GPU） | ≈22 ms | **44.8 ms**（p95 54.1） | ×2.03 |
| 混淆矩阵 | 72/21/5/93 | 70/23/5/93 | 漏报多 2 例 |

**读法：**

- **误报一例没涨、mAP 持平**，说明判定链本身对分辨率不敏感——变的是检测出的框，不是规则。
- **漏报涨了 2.15 点**：上采样是插值放大，再 letterbox 回 640，等于额外加了一层模糊，
  远处小目标更难认。这是「输入质量」的代价，不是阈值问题。
- **单帧翻倍到 44.8 ms**：大图 letterbox 的开销，仍在 50 ms 目标内但已接近上限。
  真要接 1080p 摄像头，这条比精度更先成为瓶颈（见第 3 节耗时口径）。

> ⚠️ 这份素材是**上采样**，不是真实 1080p 摄像头录像，所以它只证明「分辨率变化下的稳健性」，
> 不能当成「现场 1080p 实测」。真实素材到位后要重跑并替换本表。

## 五、改了东西之后，按这个顺序同步

```
config/thresholds.json  ──改阈值──>  sweep_rules/geom  ──>  evaluate_real.py
        │                                                        │
        └──> 本文第一节                        ┌─────────────────┘
                                              ▼
                        data/metrics_*.json  ──>  README 第五节 / 技术页 P11 / 交付清单
                                              │
                                              └──>  python src/anxun/verify_all.py
```

`verify_all.py` 里有六条硬检查专门防口径分叉：

- `config/thresholds.json` 能加载，且 `measured` 与代码里生效的常量一致；
- 每份 `data/metrics_*.json` 都记录了自己是哪个口径跑的（`config.rules_profile`）；
- 两份口径的判定行为确实不同（同一输入 0.52 的帽框：measured 判「已佩戴」，conservative 判「待复核」）；
- 技术页页脚标注了阈值口径，关键数字与 JSON 对得上；
- `docs/figs/` 三张图已生成（JSON 有数、图上没东西等于没做）；
- `datasets/*/data.yaml` 不含本机绝对路径（否则换台机器就跑不动）。

任何一条不过，说明材料里有一个数是旧的。
