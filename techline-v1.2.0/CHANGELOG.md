# 变更日志

## v1.2.0 — 2026-11-02

这一版不碰模型、不动指标。主线是**把交付口径收敛成一套**：此前同一份作品并存着两套阈值、
三个耗时版本、两套类别口径，评委当场就能撞出来。版本号进一位，是因为交付物里新增了三份文件
（口径表 / 置信区间 / 三张图），口径本身也变了。

### 判定阈值：从「写死在代码里」改成「一份配置，两个名字」

- 新增 **`config/thresholds.json`**：阈值唯一事实来源，含两套 profile ——
  `measured`（0.30 / 0.20 / IoU 0.25，交付与评测默认）与 `conservative`（0.60 / 0.40，演示用）。
- `rules_engine.py` 启动时加载配置，模块常量由 `apply_profile()` 赋值；`pipeline.thresholds()`
  改为读 `profile_snapshot()`，不再各存一份。`/api/scenes` 因此会带上当前口径名。
- 切换方式：`ANXUN_RULES_PROFILE=conservative`、`--profile conservative`（`app.py` / `evaluate_real.py`）
  或代码内 `apply_profile()`。
- `evaluate_real.py` 把口径写进结果 JSON（`config.rules_profile`）；`data/metrics_real.json`、
  `metrics_onnx.json` 已补标 `measured`。
- **实测回归**：重跑 `evaluate_real.py` 得到 0.6808 / 5.10% / 22.58% / 72-21-5-93，与改造前逐位一致。

> 配套动作：其它文档里若还留着 0.60 / 0.40 的旧阈值表，请直接换成
> [`docs/技术口径.md`](docs/技术口径.md) 第一节。

### 耗时口径：一个数，四个条件

- README 2.1 与 `docs/模型卡片.md` 里的 **53.5 ms 作废**（未锁 `onnxruntime` 版本的旧数），
  统一为 ONNX-CPU **72.7 ms**、torch-GPU **≈22 ms**（均为 `evaluate_real.py` 在 100 张上的均值；
  torch-GPU 三次复跑 21.8 / 22.4 / 22.1 ms，取近似值，精确值以 `data/metrics_real.json` 为准）。
- 启动自检的 8.8 / 31.7 ms、批处理的 6.9 / 7.1 ms 明确标注为「非指标口径」。

### 判定与编排修复（对外交付前最后一轮）

都是「能跑、不报错、但结论悄悄错」的那类问题，逐条配了回归测试
（`tests/test_techline.py`，13 条，`python -m unittest discover -s tests`）：

- **择优非单调**（`rules_engine._score`）：原来按 `(IoU, 包含度)` 取全局最大，
  一个「IoU 略高、两项都不达标」的废框能顶掉包含度 1.0 的正确框，把「已佩戴」翻成
  「未佩戴」。改为**先取达标框、无达标才回落**。实测 100 张测试集四项指标逐位不变。
- **装备清单不跟模型走**（`catalog` 硬写 `helmet+vest`）：缺 vest 权重时模型不产背心框，
  规则引擎判「全体未穿背心」——「全员正确佩戴、应放行」的场景会直接报一条黄色违规。
  新增 `detectors.available_equips()`，场景意图与模型能力求交集，缺项整条跳过并在
  输出里标 `degraded`。单路 `stream.py`、多路 `scheduler.py` 同步。
- **单图硬凑多帧**（`pipeline.inspect`）：`frames>1` 时把同一张图推理三遍，
  「连续 3 帧一致」必然成立。现在无 `scene["images"]` 一律按单帧处理，
  输出带 `temporal.aggregated / used`，别在界面上写不存在的时序确认。
- **时序聚合串人**（`aggregate_temporal`）：帧间判定项数不一致时按下标比会张冠李戴，
  改为整体转「待复核」并说明原因（视频链路是「一条轨迹一个窗口」，不受影响）。
- **`--vest` 是空参数**（`evaluate_real`）：只声明不接线，导致「加 vest 不影响 helmet 指标」
  无法复现。现已接线，实测加背心后 0.6808 / 5.10% / 22.58% / 72-21-5-93 逐位不变，
  单帧 ≈22 → ≈32 ms。
- **漏报率分母缺陷**（`evaluate_real` + `metrics`）：没检出的人原来直接从分母消失。
  现在真值里能判的人一律记录并标 `matched`，`metrics` 同时给出 `matched`（判定层）
  与 `e2e`（整条链路）两套数：5.10%/22.58% 与 4.67%/**31.43%**，覆盖率 90.1%。
  headline 默认仍是 `matched`，`--metric-scope e2e` 可切换。
- **服务并发**（`app.py`）：`ThreadingHTTPServer` + 单例检测器（ultralytics predict 与框缓存
  都不是线程安全的）没有任何互斥，并发请求会串结果。加推理锁；临时文件改用 `mkstemp`；
  `/docs/` 与 `image_path` 的路径校验从字符串前缀改成 `Path.is_relative_to`；
  `/health` 的 `uptime_s` 改用 `total_seconds()`（原来跑满一天归零）。
- **`--backend onnx` 会覆盖 GPU 交付指标**（`evaluate_real`）：默认落盘写死
  `data/metrics_real.json`，跑一次 CPU 口径就把 GPU 的四个交付数字换成另一套，且没有任何提示。
  改成按后端决定默认文件（torch → `metrics_real.json`，onnx → `metrics_onnx.json`）；
  显式指向另一个后端的交付文件时直接拒绝，要覆盖得加 `--force`。
- **1080 复验的真值口径与指标不是一套**（`tools/verify_trigger_1080.py`）：原来用
  「装备框与人员框 IoU ≥ 0.5」判真值，helmet 只算出 **1 人次**，而同一批图的指标是 93 人次
  （真值 105）——「触发层有没有跳掉真违规」这项检查等于空跑却一直 PASS。现已改用与
  `evaluate_real.truth_of` 同一判据（装备框中心落在人员对应区域），helmet 105 人次，
  与 `metrics_1080.json` 的 e2e 分母对齐。
- **请求体无上限、ONNX 线程池不回收**（`app.py` / `onnx_backend.py`）：一个声明的
  `Content-Length` 就能让 `rfile.read(n)` 吃光内存（服务是 `ThreadingHTTPServer`，
  一个连接拖垮全部线程），加 16 MB 上限并回 413；`OnnxDualDetector` 补 `close()`
  释放并发池与 session，服务退出时调用（验收脚本会反复构造 detector，不回收会累积线程）。

### ONNX-CPU 三模型并发：72.7 → 46 ms（输出逐框不变）

CPU 路径原来串行跑三个模型，且每个模型各做一遍预处理。两处都是白等/白算：

- **预处理只算一次**：三个模型 imgsz 都是 640，同一张图的张量完全一样。
  抽出 `OnnxDetector.preprocess()` / `infer_tensor()`，`OnnxDualDetector` 复用同一份张量（省 ≈6 ms）。
- **单图路径三模型并发**：`detect_image` 把三个 session 丢进 3 线程池，`session.run` 释放 GIL，
  真并行（省 ≈20 ms）。`detect_frame` 保持「先人体 → 门控 → 再跑装备」的串行顺序——
  视频里大部分帧没人，门控省的前向比并发值钱。
- **零碎**：letterbox 输入已是目标尺寸时不 resize 不拷贝；归一化改原地乘。

结果：**ONNX-CPU 单帧 72.7 → 46.1 ms（p95 82.4 → 49.1）**，两次复跑 46.10 / 46.11。
权重、预处理、decode、NMS 全没改，10 张图逐框比对完全一致，
`evaluate_real.py --backend onnx` 重跑四项指标逐位不变（当时的几何口径：0.6808 / 5.10% / 22.58% / 72-21-5-93）。

边界：只在逻辑线程 ≥12 时开并发，小机器自动退回串行（预处理复用仍生效）；
`ANXUN_ONNX_PARALLEL=0` 可强制串行。做法与验证写在 `docs/技术口径.md` 3.2。

### 判定阈值复扫：把误报预算换成漏报（22.58% → 17.20%）

误报率 6.12% 距目标（≤10%）还有 4 个点没花，而漏报是最短板。复扫几何阈值后，
把 helmet 从 `iou 0.25 / contain 0.60` 收到 `0.28 / 0.70`——模型误检出的帽子往往
只盖住头部区域一小半，包含度判据正好过滤这一类。

| 数据 | 误报 | 漏报 |
| :--- | ---: | ---: |
| test（640×640） | 5.10% → **6.12%** | 22.58% → **17.20%** |
| test1080（3× 上采样） | 5.10% → 7.14% | 24.73% → **18.28%** |

mAP 不变（0.6808 / 0.6829），混淆矩阵 72-21-5-93 → 77-16-6-92。两套数据同向改善，
不是单集挑点。连带的数字全部重算：三份 metrics JSON、Wilson 置信区间
（误报 2.8–12.7%、漏报 10.9–26.1%）、三张成品图，以及 README / 技术页 P11 /
技术口径 / 交付清单。

`verify_all.py` 的技术页数字检查改为从 `metrics_real.json` 取期望值，不再写死——
v1.2.0 期间就漏过一次同步。

## v1.1.0 — 2026-11-01

这一版不加架构、不换模型。主线是「把已经能跑的东西交付干净」：权重与评测集随仓库走、口径对齐、
把一处过保守的判定闸门校准回来。mAP 与误报率不动，漏报率小幅下降。

### 变更

**判定链**

- `MIN_ASPECT` 1.20 → 0.90（`rules_engine.py`）。4 例触发该闸门的样本逐张复核：蹲姿 2 例的头部
  仍落在「人体框顶部 30%」判定区内，判「无法判定」等于白丢告警；弯腰 2 例头部已偏出区域，继续不判。
- 影响：漏报率 **24.73% → 22.58%**（n=93，恢复 2 例），误报率 **5.10% 不变**，mAP@0.5 **0.6808 不变**；
  背心漏报 12.97% → 11.35%。

**交付形态**

- 模型权重入库：3 个 `.pt` + 3 个 `.onnx` + manifest（约 101 MiB）。此前仓库不含权重，
  clone 下来服务起不来、指标无法复现。`hardhat_m.pt`（49.6 MB，仅 `sweep.py` 架构对比用）仍排除。
- 评测集入库：`datasets/ppe_test/`（100 测试 + 100 训练 + 标注，14 MB，CC BY 4.0）。
  四个指标现在可在仓库内一键复现，实测与 `data/metrics_real.json` 逐位一致。
- 演示素材入库：`datasets/scenes/`（4 张，300 KB），控制台不再空白。
- 1080p 复验素材（51 MB）与 `helmet_p2` 训练集（60 MB）仍不入库，`tools/` 里的脚本可重建。

**验收脚本 `verify_all.py`**

- 新增 `skip()`：依赖没随仓库分发时记 SKIP，不计 PASS/FAIL —— 缺件和「东西坏了」分开报。
- 新增「ONNX 后端可加载并前向」硬检查（权重损坏会在这里暴露，而不是等换机器）。
- 无评测集时改用合成探针图做推理烟测，不再抛 `IndexError`。
- 新增「README 版本号与包版本一致」检查；验收报告 JSON 写入 `version` 字段。
- 当前：仓库直接跑 **37 项 34 PASS / 0 FAIL / 3 SKIP**；补齐训练集与 1080p 素材后 **37 项全 PASS**。

**依赖**

- `requirements-cpu.txt` / `requirements-gpu.txt` 全部改为精确版本，取自实测环境
  （onnxruntime 1.31.1 · ultralytics 8.4.99 · opencv-python 5.0.0 · numpy 2.5.4 · torch 2.14.1 · torchvision 0.29.1）。
  此前一直是 `>=` 软约束，是 ONNX 单帧从 53.5 ms 漂到 72.7 ms 的根因——同一模型、同一台机器，
  版本一换耗时差 40% 且无法归因。
- 两个文件都注明：改版本必须重跑 `evaluate_real.py --backend onnx` 并更新 README 2.1 的复测记录。

**文档**

- 新增 `docs/交付清单.md`：按赛题四项（能跑的模型 / 四个指标 / PPT 10–13 / 部署）逐项对照，
  并把「数据、模型、指标、部署、技术页」五块职责映射到具体文件与验证方式。
- README 2.3 重写：仓库里有什么、没什么，clone 后三步跑通。
- `docs/模型卡片.md` 权重获取一节改写（随仓库分发 + SHA256 自核）。
- 技术页 P10/P11 数字与实测对齐（混淆矩阵 72/21/5/93、漏报归因 21 例、单帧 22.9 ms），
  补第⑥步优化；P11 说明块精简，避免溢出 720px 画布。

## v1.0.0 — 2026-10-31

首个可运行交付版本。

- 三模型串联：人体（yolov8n）+ 安全帽（yolov8s-hard-hat）+ 反光背心，`.pt` / `.onnx` 双份。
- 四态判定（已佩戴 / 未佩戴 / 待复核 / 无法判定）+ 三帧时序聚合 + R=L×S 风险定级 + 工单生成。
- 三级触发（抽帧 / 帧差 / 门控）、多路锁步攒批、判定与推理解耦。
- 四个指标：mAP@0.5 0.6808 · 误报 5.1% · 漏报 24.73% · 单帧 24.9 ms（GPU）/ 53.5 ms（ONNX-CPU）。
- 技术页 P10–P13（`docs/技术页_10-13.html`，4 页 16:9）。
