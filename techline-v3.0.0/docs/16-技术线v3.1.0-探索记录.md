# 技术线 v3.1.0 · 探索记录（五条死路 + 一条活路）

> 2026-11-03 · 最初目标：压 v3.0.0 唯一破线的指标——**误报 10.20%**
>
> **一句话概览**：前面五条路（提分辨率 / 降阈值 / 局部放大 / 放宽区域 / 降 person conf）全部实测否掉，
> 因为它们都在**判定层**打转。真正的转机在**检测层的数据**——找回源数据集重新训练，
> 再换成 s 骨干、合并成单模型，四项指标里三项达标。见第五节。

---

## 一、先归因，再动手

不对症调参等于闭眼改数字。先把 10 例误报逐例拆开（`tools/attr_fp.py` →
`data/fp_attribution.json`，每例带裁图 `runs/_review_fp/`）。

| 原因 | 例数 | 含义 |
|---|---:|---|
| B2 置信度不够 | 6 | 框在头部区域内，但 conf < 0.59 |
| B3 中心点出区 | 2 | 框够置信，中心点落在区域外 |
| B1 模型没检出 | 2 | 头部附近压根没有 helmet 框 |

第一版归因一度让人以为「60% 是阈值卡掉的」，**这个判断被后续数据推翻过一次**：
B2 的 6 例里有 5 例在区域外还有个 0.715–0.886 的高置信框，看起来像「区域估偏了」。

于是又算了一步：把标注框（GT）的中心相对 person 框的位置列出来——

| | GT 框中心 y 比例 |
|---|---|
| 10 例全部 | **0.02 – 0.20** |

判定区域是纵向 0–0.26。**标注框中心全都在区域内**，说明区域没估偏，
人确实戴了帽子，就是模型在自己头上给的置信度不够。

> 那 5 个「区域外高置信框」是什么？算了 dx（以区域宽度为单位）：**0.58 到 15.35**。
> dx=10 意味着偏了 10 个区域宽度——那是画面另一边的人。**不是这个人的，是别人的头盔。**

## 二、五条路线，五条死路

### 路线 1：提高全图推理分辨率

假设：6 例里 3 例 conf 只有 0.25–0.31，且 person 框宽仅 44–93 px，是典型小目标。
放大输入应该让头变大、置信度上去。

| 方案 | mAP@0.5 | 误报 | 漏报 | 单帧 |
|---|---:|---:|---:|---:|
| **基线 640** | **0.7758** | **10.20%** | **16.13%** | **19.5 ms** |
| 960 | 0.7864 | 18.09% | 16.13% | 29.5 ms |
| 1280 | 0.7213 | 34.09% | 21.51% | 40.2 ms |

**否。** 960 的 helmet AP 确实涨了（0.7545 → 0.7798），但误报从 10.20% 翻到 18.09%；
1280 全面崩盘。根因是**模型在 640 上训练**，放大推理等于把目标推出训练分布——
框的位置和置信度分布都变了，中心点判据随之失效。

这与 v2.2 时期的发现一致（s @960 掉点），不是新问题。

### 路线 2：降阈值

`docs/15` 已扫过，属于已知权衡曲线：

| conf | 误报 | 漏报 |
|---|---:|---:|
| 0.45 | 7.14% | 23.66% |
| 0.55 | 8.16% | 19.35% |
| **0.59（当前）** | **10.20%** | **16.13%** |
| 0.65 | 16.33% | 15.05% |

**否。** 误报能降到 7.14%，代价是漏报涨 7.5 个点。安全场景里漏报比误报贵，
这笔交换不能做。

### 路线 3：只对「未佩戴」的人做头部放大复核（两级判定）

假设：既然全图放大不行，那只把可疑那个人的头裁出来放大——不影响其他人。

先做可行性探针（`tools/probe_head_zoom.py`）：10 例误报里 **3 例**能被放大救回。

| 案例 | person 框 | 全图 conf | 放大后 conf |
|---|---:|---:|---:|
| case1 | 306×635 | 0.581 | **0.743** |
| case2 | 137×467 | 0.252 | **0.813** |
| case4（B3） | 51×306 | 无 | **0.765** |

看起来成立。于是全量集成（`tools/eval_two_stage.py`）：

| 方案 | 误报 | 漏报 | 单帧 |
|---|---:|---:|---:|
| 基线 | 10.20% | 16.13% | 19.5 ms |
| 两级判定 | **9.18%** | **20.43%** | 44.2 ms |

**否。** 误报只降 1 个点，漏报涨 4.3 个点。二级复核共翻案 6 例，
其中 **5 例翻错**（把真正没戴的人判成戴了）。

根因：模型在「纯头部特写」上的假阳性率远高于全图。训练数据里没有这种构图，
裁剪放大引入了分布偏移——和路线 1 是同一个病。

### 路线 4：放宽判定区域

`docs/15` 附录 B.3 只扫过**收紧**（0.22 / 0.18 / 0.15），从未试过**放宽**。
6 例 B2 的 GT 框中心 y 都在 0.02–0.20，理论上区域盖得住；放宽也许能把
「区域外高置信框」纳进来。

扫了 5×3 = 15 组（region 0.26–0.44 × width 0.70–0.90，`tools/sweep_region_v3.py`）：

| region / width | 误报 | 漏报 |
|---|---:|---:|
| 0.26 / 0.70（基线） | 10.20% | 16.13% |
| 0.30 / 0.80 | 10.20% | 16.13% |
| 0.38 / 0.90 | 10.20% | 16.13% |
| 0.44 / 0.90 | 10.20% | 16.13% |

**15 组，指标一格没动。** 这反而证实了第一节的结论：那些高置信框离得太远，
不是这个人的头。区域放宽只是把别人的框圈进来，而它们的中心点依然不落在本人头上。

### 路线 5：降低人体检测置信度（e2e 口径的最后一块）

前四条都在压 matched 口径的误报，但同一批数据换 **e2e 口径**（连没检出的人一起算）
漏报是 **25.71%**，比 matched 的 16.13% 高 9.6 个点——差出来的 12 例是「人压根没检出」。
这一层从没单独动过：`DualDetector` 的 conf 是 person 与 ppe 共用，调它等于同时改两个模型。

于是单独改 `det.person.conf`（`tools/probe_person_conf.py`）：

| person conf | 检出人数 | 覆盖率 | matched 误报/漏报 | **e2e 误报/漏报** |
|---:|---:|---:|---|---|
| 0.25（当前） | 297 | 90.09% | 10.20 / 16.13 | 9.35 / **25.71** |
| 0.20 | 322 | 90.57% | 10.10 / 16.13 | 9.35 / **25.71** |
| 0.15 | 360 | 92.45% | 10.00 / 18.75 | 9.35 / **25.71** |
| 0.10 | 416 | 93.87% | 9.80 / 19.59 | 9.35 / **25.71** |

**e2e 一例没降。** 检出人数多 119 人、覆盖率涨 3.8 个点，漏报纹丝不动（始终 27/105）。

拆开看：conf 0.10 时 matched 的违规人次从 93 涨到 97（多认了 4 个），
但这 4 个人**全部被判「已佩戴」**——低质量人框的头部区域里挂着假头盔框。
于是 matched 漏报从 15 涨到 19，e2e 仍然是 15→19 加 8 个未匹配，净额不变。

**否。** 这 12 例不是「阈值低一点就能救」的，是那些人本身的框质量不足以支撑判定。
v3.0.0 选 conf 0.25 是对的。

## 三、视频级验证：第一次把「时序聚合后」的指标算出来

前两节都是单帧口径（100 张静态图，每张独立判定）。真实部署是视频，
`aggregate_temporal` 要求**连续 3 帧结论一致才定论**——这两件事的指标不是一回事，
但之前只报了单帧那一套。

### 3.1 先修了一个真缺陷

账本的判定记录里**没有人员框坐标**，只有 track id 和时间。第一版按时间窗对齐真值，
12 个人全被配成「未佩戴」、误报假 100%——多人同框时时间窗分不清谁是谁。
给 `_book()` 加 `bbox` 字段后，改成「时间窗筛候选 + 框 IoU 定人（含平移补偿）」才对上。

### 3.2 素材：重新造了一批带违规的

原 `site_pan.mp4` 的 12 个人头盔**全是合规的**，只测得了误报。
`make_motion_video.py` 的采样原来按文件名顺序取，改成按「是否含头盔违规」分层：

    python tools/make_motion_video.py --out datasets/site_pan_v2.mp4 \
        --truth data/site_pan_v2_truth.json --scenes 10 --violation-scenes 0.5 \
        --pan-s 3.0 --hold-s 4.0 --gap-s 1.2

产出 26 人（12 违规 / 14 合规）、88 秒、每人停留 8.2 秒（约 16 个抽样帧）。

### 3.3 结果

| 装备 | 可判人次 | 视频级误报 | 视频级漏报 | 混淆矩阵 |
|---|---|---|---|---|
| **helmet** | 合规 7 / 违规 5 | 71.43% | **0.00%** | tp 5 · fn 0 · fp 5 · tn 2 |
| **vest** | 合规 2 / 违规 11 | 50.00% | **9.09%** | tp 10 · fn 1 · fp 1 · tn 1 |

对照单帧口径（100 张静态图）：误报 10.20%、漏报 16.13%。

**两个数都还不能当交付指标用**，原因有三：

1. **26 人里 14 人（54%）没有判定记录**——集中在 3–4 人的密集场景。
   延长停留时间（4.8s → 8.2s）没有改善，说明不是帧数不够，是遮挡导致轨迹碎裂。
2. 样本小：helmet 合规只有 7 人次，一例就是 14 个百分点。
3. 素材是「整幅照片平移」的合成画面，人物边缘有伪影，与真实监控差距大。

**但方向上有个一致的现象**：违规检出很稳（漏报 0% / 9.09%），误报高（50–71%）。
也就是说**时序聚合让「该报的」更稳，但没有压住「不该报的」**——
在合成素材上，误报反而比单帧更高。这与单帧的结论（漏报是短板）正好相反，
说明两种口径衡量的是不同东西，不能互相替代。

## 四、结论

**五条路，全部否掉。v3.0.0 的 0.7758 / 10.20% / 16.13% 是这套权重 + 这套判据的局部最优。**

> ⚠️ **注意：这个结论后来被推翻了**——不是「单帧到顶」，而是「在**这套数据和这套权重**上到顶」。
> 换数据 + 换骨干之后，同一批评测集上 mAP 从 0.7758 推到 0.8654。见第五节。

真正的原因收敛成一句话：

> **瓶颈不在判定层，在「640 输入下头只有 20–30 px」这个物理事实。**
> 模型不是判错，是看不清；判据不是不灵，是没有足够的信息可判。

这也是为什么五条路都通向同一个死胡同：
- 提高分辨率 → 出训练分布
- 放大局部 → 引入新分布
- 改区域 → 治不了置信度
- 改阈值 → 只是把错误在误报/漏报之间搬家

## 五、终章：换数据 + 换骨干（这条路走通了）

前四节都在**现有权重 + 现有数据**里打转，所以全部撞墙。转机来自跳出这个框。

### 5.1 找回源数据集，先剔干净

v3.0.0 的训练集 `ppe1206`（1206 张）原图丢了，但源数据集还在——
`Chapian/ppev3` 的 `PPE DETECTION.v3i.coco.zip`（Roboflow `ppe-detection-9p0pu` v3，
2896 张、32498 框、9 类、CC BY 4.0、已 resize 到 640）。

**关键：必须先剔除评测集。** `ppe_test` 的 200 张（train 100 + test 100）全部来自这个源集：
test 里 **65 张**重名、train **100 张**全重名。不剔除就是训练集里混着测试图。

    python tools/build_ppe_full.py

产出 `datasets/ppe_full`：**2451 训练 / 272 验证**（剔除 165 张重叠 + 8 张无有效框），
9 类重映射为 5 类（丢弃 boots / gloves / no_boots / no_gloves）。

### 5.2 骨干 n → s

`yolov8s` @640、80 轮、batch 16，验证集 **mAP50 0.8857**（best ep62）。

### 5.3 双模型 → 单模型

新五类权重自带 `person`，不需要再外挂 COCO `yolov8n`。但这里踩了一个坑：

`DualDetector._merge` 假设「person 模型只出 person」。传同一个权重给 `--weights` 和
`--person-weights` 时，person 模型的**全部**框（含 helmet/vest）会和装备框拼在一起——
helmet 框 2 个变 4 个、fp 27 → **189**、helmet AP 从 0.87 掉到 **0.45**。
这不是模型问题，是拼框逻辑的假设失效。改成 `single` 模式（路径相同时复用实例、只前向一次）后正常。

### 5.4 结果

| 指标 | v3.0.0 | **v3.1.0** | 目标 | 判定 |
|---|---:|---:|---:|---|
| mAP@0.5 | 0.7758 | **0.8654** | ≥0.85 | ✅ |
| 误报率 | 10.20% | **6.12%** | ≤10% | ✅ 余 3.9 点 |
| 漏报率 | 16.13% | **6.52%** | ≤5% | ❌ 差 1.5 点 |
| 单帧耗时（GPU） | 19.5 ms | **11.8 ms** | ≤50 ms | ✅ 4.2× 余量 |

漏报那 6 例里，**4 例是「无法判定」转人工**（目标过小 / 半身），只有 **2 例**是真判错。

### 5.5 为什么前五条会全撞墙

因为它们都在调**判定层**，而瓶颈在**检测层的数据**。

> 前五条是在一间没有窗户的屋子里找出口；第六条的答案是「换一间屋子」。

### 5.6 附带发现：v3.0.0 的 0.7758 是虚高的

`ppe1206` 从源集切出时没有排除评测集，100 张里有 **65 张被训练见过**。
把评测集按「是否重叠」拆成两组、同一个模型跑：

| 组 | 图数 | helmet AP | 误报 |
|---|---:|---:|---:|
| 在源集中（可能见过） | 65 | **0.8312** | 8.05% |
| 不在源集（确定没见过） | 35 | **0.2369** | 27.27% |

两组人框边长中位 208 px vs 141 px，目标大小相近，差 **0.59** 只能由泄漏解释。

**这也解释了为什么前五条会全部失败**：它们是在一个被污染的评测集上找提升空间，
而那个 10.20% 本身就不稳。

### 5.7 试过 yolov8m，不换

同一份数据、同样 80 轮，训了 `yolov8m`（best ep68，验证集 mAP50 **0.8953**，比 s 高 0.0096）。
主口径实测：

| 模型 | mAP | helmet AP | 误报 | 漏报 | 耗时 | 权重 |
|---|---:|---:|---:|---:|---:|---:|
| **s（采用）** | 0.8654 | 0.8845 | **6.12%** | **6.52%** | **11.8 ms** | 22 MB |
| m | **0.8740** | **0.8973** | 5.05% | 7.53% | 20.0 ms | 50 MB |

mAP 高 0.009、误报低 1 个点，但**漏报反而差 1 个点**——而漏报是唯一没达标的指标。
阈值曲线也扫了（0.30–0.85），同样没有交点：0.70 → 8.16 / 7.53，0.75 → 10.20 / 6.45，
都差于 s 的 0.65 → **6.12 / 6.52**。

**结论：不换。** 多付 70% 耗时、2.3 倍体积，换 0.009 的 mAP 和更差的漏报，不划算。
`models/best.pt` 保持 s 版本，m 的权重留在 `runs/ppe_full_m/`（不入库）。

## 六、还剩什么

| 选项 | 状态 | 结论 |
|---|---|---|
| ~~重训 @960~~ | **已试，失败** | 用 `helmet_p2`（1600 张、2 类）训：640 推理 helmet AP **0.1946**、960 推理 **0.2337**，比 640 训练/推理的 0.75 差 3 倍。验证集 mAP50 能到 0.9524，但那是「自己人考自己人」——跨到评测集就崩。根因是**数据分布**，不是分辨率 |
| **换源数据重训** | **已做，成功** | 见第五节：**0.8654 / 6.12% / 6.52% / 11.8 ms** |
| ~~补「普通帽子」负样本~~ | 仍缺数据 | 但影响已从 5 例降到 **2 例**（剩下的真判错只有软布帽） |
| 补 vest 数据 | 仍缺数据 | 视频级验证里 vest 已是 0% 误报 / 9.09% 漏报，优先级低 |
| 参数/判据继续调 | 已证伪 | 五条路线 + `conf_final` 全区间（0.30–0.85）扫描，**无交点** |

**现在的短板只有一个**：漏报 6.52%，距 5% 差 1.5 点。往下一层看，6 例里 4 例是「无法判定」
（目标过小 / 半身，转人工），2 例是软布帽判错。要再压只能补软帽负样本重训——
本地已无数据，且这 1.5 点本身就落在 100 张的样本误差内（每例约 1.09 个百分点）。

**建议**：技术线到此为止，把时间转去 PPT / 视频 / 答辩。

> **一个值得记住的教训**：前五条路全部失败时，我们的结论是「单帧到顶」。
> 那个结论错在把「这套数据的上限」当成了「这个方法的上限」。
> 真正的瓶颈往往不在你正在调的那一层。

## 七、复现

```bash
python tools/build_ppe_full.py              # 从源数据集重建五类训练集（剔除评测集）
python tools/train_ppe1206.py --data datasets/ppe_full --arch s \
    --init models/yolov8s.pt --imgsz 640 --batch 16 --epochs 80 --name ppe_full_s
python tools/probe_target_reach.py         # 阈值全区间扫描：能不能同时达标
python src/anxun/evaluate_real.py          # 四个指标（单模型 + v3 口径）
python tools/attr_fp.py                    # 误报逐例归因（10 例 + 裁图）
python tools/probe_head_zoom.py            # 头部放大的可行性探针
python tools/eval_two_stage.py              # 两级判定全量评测
python tools/sweep_region_v3.py             # 判定区域 15 组扫描
python src/anxun/evaluate_real.py --imgsz 960  --out data/metrics_imgsz960.json
python src/anxun/evaluate_real.py --imgsz 1280 --out data/metrics_imgsz1280.json
```

全部数字在 `data/` 下：`fp_attribution.json` / `head_zoom_probe.json` /
`metrics_two_stage.json` / `metrics_imgsz960.json` / `metrics_imgsz1280.json`。
