# 03 · 技术架构

> 一句话：**检测模型负责「看得见」，规则引擎负责「判得准」，Agent 负责「办得成」。三者解耦。**

---

## 一、为什么必须解耦

### 1.1 架构

```
┌────────────────┐      ┌────────────────┐      ┌────────────────┐
│   检测模型      │ ───> │   规则引擎      │ ───> │  Agent 编排     │
│   看得见        │      │   判得准        │      │   办得成        │
│   YOLO11 / RT-DETR │  │  纯 Python      │      │  扣子工作流      │
└────────────────┘      └────────────────┘      └────────────────┘
   infer_api.py           rules_engine.py         提示词 + 知识库
   HTTP 接口，可替换        确定性，可复现            对话 + 调度
```

### 1.2 四条好处（答辩可以直接说）

| 好处 | 具体表现 |
|---|---|
| **模型没训好也能演示** | 规则引擎跑模拟框就能出完整结果，`demo.py` 零依赖可跑。**这是当前状态** |
| **换模型不影响业务逻辑** | YOLO 换 RT-DETR 只改 `infer_api.py` |
| **换平台不用重写** | 扣子换 JoyCode 只改调用地址 |
| **结果可复现** | 同一输入永远同一输出，答辩敢让人当场重算 |

> 第三条在答辩现场很值钱。评委问「你怎么保证定级不是模型随便说的」，你可以说「我现在就可以重跑三次给你看」。

### 1.3 关键决定：模型必须独立成 API

不要塞在 Agent 内部。三个理由：

1. **平台迁移时不重写**——Coze 换 JoyCode 只换调用地址
2. **评委能直接访问接口验证**——`GET /health` 就能看到服务活着
3. **模型迭代不影响上层**——重训完换个 `MODEL_PATH` 就行

## 二、数据流

```
摄像头 / 视频文件
      │
      ▼  抽帧
   检测模型 API (infer_api.py)
      │  boxes: [{label, conf, x1,y1,x2,y2}, ...]
      ▼
   ② 视觉感知 Agent ── 四态判定
      │  verdicts: 已佩戴 / 未佩戴 / 无法判定 / 待复核
      ▼
   ③ 隐患研判 Agent ── 处置等级定级（按确认人数分档）
      │  event: {grade: A/B/C, 处置要求, 时限}
      ▼
   ④ 工单闭环 Agent ── 生成可执行工单
      │  ticket: {责任人, 时限, 整改动作, 复查时间}
      ▼
   复查归档
```

### 旁边三条支线

- **① 巡检规划** 在每日开始产出计划，决定拍哪里
- **⑤ 合规问答** 随时被 ③④ 调用取法规依据
- **历史数据回流** 给 ① 和 ③，让风险加权和 L 值算得出来

## 三、四态判定（第②层的核心）

### 3.1 为什么是四态，不是两态

大多数方案只输出「戴了 / 没戴」。这在工业场景里不可用，因为模型永远有不确定的时候，强行二分会把不确定性变成误报。

所以我们锁死四种输出：

| 状态 | 触发条件 | 后续动作 |
|---|---|---|
| **已佩戴** | 头部区域检出装备框，IoU ≥ 0.25 且置信度 ≥ 0.30 | 放行，记录 |
| **未佩戴** | 头部区域未检出装备框（最高 IoU < 0.25），且人员框质量合格 | 进入风险定级 |
| **待复核** | IoU 成立但置信度落在 [0.20, 0.30) | 转人工，不自动定级 |
| **无法判定** | 人员框面积 < 8000 px² 或高宽比 < 0.90 | 直接拦截，不输出违规 |

> 关键设计：**「无法判定」不是「未佩戴」。** 宁可说不知道，也不要猜。

### 3.2 几何判定怎么做

不训练额外的分类器，纯几何 + 置信度规则：

```
1. 取人员框
   ├─ 面积 < MIN_PERSON_AREA (8000 px²)  → 无法判定（目标过小）
   └─ 高宽比 < MIN_ASPECT (0.90)         → 无法判定（半身/蹲姿）

2. 划头部区域
   头部区域 = 人员框上部 HEAD_REGION_RATIO (30%)

3. 找落在头部区域的装备框
   对每个装备框计算 IoU(装备框, 头部区域)
   取最大 IoU

4. 三档判断
   ├─ max_IoU >= 0.25 且 conf >= 0.30     → 已佩戴
   ├─ max_IoU >= 0.25 且 conf ∈ [0.2,0.3) → 待复核
   ├─ max_IoU >= 0.25 且 conf < 0.20      → 丢弃
   └─ max_IoU < 0.25                       → 未佩戴
```

同样的逻辑复用到反光背心（上身区域，即人员框 30%–75% 高度段）。

护目镜（`goggles`）是预留类别：代码里保留了判定分支与法规条目，但**没有数据、没有权重，当前不启用**。对外只说三类。

### 3.3 三个阈值怎么定

> **这一节讲的是系统线（demo / Agent）的演示口径**，实现在根目录 `src/anxun/rules_engine.py`。
> 技术线 v3.1.0 的评测口径是另一套：`conf_final 0.65` / `conf_review 0.20`，且 helmet 改用
> **中心点判据**（不再看 IoU），见 `techline-v3.1.0/config/thresholds.json` 的 `v3` profile。
>
> 为什么不统一：v3 换成自训五类权重后，头盔框比第三方权重贴得更紧，旧 IoU 判据在 640 输入下
> 会把「戴了」判成「没戴」（头部区域只有 31 px 宽，头盔框本身 29 px）；改判据必须同时抬阈值。
> 演示口径保持 0.30 是为了四态齐全、能演出「待复核」这一档。**同一张图两边判定可能不同，
> 这是刻意的**，但对外报数只能用评测口径。

| 参数 | 值 | 依据 |
|---|---|---|
| `CONF_FINAL` | 0.30 | ≥ 此值直接下结论。**演示口径**（技术线 v3.1.0 评测口径为 0.65） |
| `CONF_REVIEW` | 0.20 | [0.2, 0.3) 转人工；< 0.2 丢弃 |
| `HELMET_IOU_MIN` | 0.25 | 安全帽框与头部区域的重叠下限。低于此值说明帽子不在头上（仅 IoU 判据生效） |
| `HEAD_REGION_RATIO` | 0.30 | 头部约占人体高度上部 30%（成人解剖比例）；技术线 v3 用 0.26 / 0.70 |
| `MIN_PERSON_AREA` | 8000 px² | 1920×1080 下约等于 20 米外的人员。**需按相机标定重设** |
| `MIN_ASPECT` | 0.90 | 人体框高宽比 ≈ 2–3；< 0.9 说明是半身或蹲姿，头部可能被裁掉 |

> ⚠️ 这些阈值是**工程经验值，不是实验最优值**。不同厂区像素尺度差异大，答辩时要主动说「`MIN_PERSON_AREA` 需按相机标定重设」——这句话反而加分，说明你懂落地。

## 四、时序聚合（第③层的入口）

### 4.1 为什么要聚合

单帧检测会抖。同一工人在连续两帧里可能一帧判「已佩戴」、一帧判「待复核」。如果每帧都出结论，会生成一堆噪音工单。

### 4.2 规则

```
连续 need=3 帧，某装备判定结果完全一致
  ├─ 状态是「已佩戴」或「未佩戴」→ 定论
  └─ 状态是「待复核」或「无法判定」→ 保持原状态，不改写

不足 3 帧一致 → 不出结论
```

### 4.3 一个坑（代码里踩过）

「无法判定」和「待复核」是**失效状态**，不能因为连续 3 帧都一致就被「提升」成有效结论。

错误写法会把「连续 3 帧都无法判定」聚合成「待复核」，相当于凭空制造了一个违规嫌疑。

正确做法（`aggregate_temporal` 里已修）：

```python
if len(seq) == need and len(set(seq)) == 1:
    st = seq[0]
    if st in ("已佩戴", "未佩戴"):
        final.append(Verdict(..., st, ..., is_violation=(st == "未佩戴")))
    else:
        # 无法判定 / 丢弃 属于失效状态，不得被改写为待复核
        final.append(Verdict(..., st, ..., last.reason))
```

## 五、处置等级（第③层的核心）

### 5.1 为什么推翻 R = L × S

v1.0–v1.3 走 MIL-STD-882 二维矩阵 `R = L × S`，前后改了四版，最后整块推翻（PPT 第 8 页讲的就是这段）。

问题出在两个输入：

- **L（可能性）** 起先取「区域近 30 天违规次数」，等于按区域过去的表现定级。同一张图换个区域登记，等级就变；刚装系统的区域台账为 0，抓到 10 人全缺 PPE 也只给最低档。
- **S（严重性）** 取作业类型，等于按场景定级。可等级要回答的是「多久内处理」，不是「这个场景本身有多危险」。

实测反例：1 人少穿背心判红色（2 小时内）、7 人全缺 PPE 判蓝色（30 天内）。

### 5.2 v1.4：按处置时限分三档

等级只回答一个问题：**这一单多久内必须处理完。** 唯一依据是本次巡检判出来的结果：

| 本次判定 | 等级 | 处理时限 | 说明 |
|---|---|---|---|
| 全场合计确认未佩戴 **≥3 人** | **A** | 2 小时内 | 已不是个别人问题，面上失控 |
| 全场合计确认未佩戴 **1–2 人** | **B** | 24 小时内 | 当日整改完并留痕 |
| 无确认违规，仅**待复核 / 无法判定** | **C** | 7 天内核实 | 进人工核实队列 |
| 全部已佩戴 | 不出单 | — | 直接放行 |

四条规则（代码在 `urgency_of()`）：

1. 等级由本次判定唯一确定，不由模型给、不允许人工调整。
2. **不看作业类型**。作业类型（`S_MAP`）只作背景记录，不参与定级。
3. **不看区域历史违规次数**。台账回答不了「这一单多久内要处理」。
4. 人数按**全场合计**算，不按单类装备拆开算——否则同一场景会出现「安全帽 B、背心 A」两张不同等级的单，一个现场两个处置时限。

### 5.3 三场景实测（线上接口真实输出）

| 场景 | 本次判定 | 本类人数 | 全场合计 | 等级 | 时限 |
|---|---|---|---|---|---|
| 2 号车间高处作业平台 | 1 人未穿反光背心 | 1 | 1 | **B** | 24 小时内 |
| 原料库装卸区 | 3 人未戴安全帽 + 8 人未穿背心 | 3 / 8 | 11 | **A / A** | 2 小时内 |
| 喷漆房 | 1 人未戴安全帽 + 5 人未穿背心 | 1 / 5 | 6 | **A / A** | 2 小时内 |

> 同一张图换到哪个区域登记，等级都不变——这是 v1.4 相对 v1.3 最关键的变化。
>
> 「喷漆房安全帽只缺 1 人也判 A」看着反直觉，但同场合计 6 人已属面上失控，且必须和背心那张单同档，否则一个现场会出现两个处置时限。
>
> 反过来，2 号车间是高处作业（旧口径下 S 最高、必判红色），但只缺 1 人，按处置时限是 B——危险程度留在作业类型里，处置紧急程度只看人数。

### 5.4 代码对应

| 位置 | 作用 |
|---|---|
| `rules_engine.urgency_of(confirmed, pending)` | 人数 → 等级 / 处置要求 / 时限 |
| `rules_engine.build_event(..., confirmed_total=)` | 定级依据写入 `Event.confirmed_total` |
| `pipeline._rule_text()` | 生成「为什么是这个等级」文案，人数取全场合计 |
| `Event.L / S / R` | 仅保留字段位（恒为 0），不再参与定级 |

完整口径见 `docs/安巡风险分级标准.md`（v1.4）；历史版本演进见 `CHANGELOG.md`。

## 六、三张核心表

不要用散落的变量，一开始就定成三张表。后面生成工单、算 L 值都靠它们。

### 6.1 区域表 `regions`

| 字段 | 类型 | 说明 |
|---|---|---|
| `region_id` | string | 区域编号，如 `A-03` |
| `name` | string | 区域名称，如「3 号车间东侧通道」 |
| `scene` | enum | 高处 / 起重 / 动火 / 车辆 / 普通 / 消防通道 |
| `risk_class` | enum | 动火 / 危化品 / 高处 / 有限空间 / 普通 |
| `owner` | string | 责任班组长 |
| `violation_30d` | int | 近 30 天违规次数（背景记录，不参与定级） |

### 6.2 事件表 `events`

| 字段 | 类型 | 说明 |
|---|---|---|
| `event_id` | string | 事件编号，如 `EV-20261103092000-B-01` |
| `region_id` | string | 关联区域 |
| `ts` | datetime | 发生时间戳 |
| `violation_type` | enum | 未戴安全帽 / 未穿反光背心 / 通道占用（未戴护目镜为预留） |
| `confidence` | float | 检测置信度 |
| `evidence` | string | 证据图路径或帧号 |
| `confirmed_total` | int | 全场合计确认未佩戴人数（v1.4 定级唯一依据） |
| `scale` | int | 本类装备确认未佩戴人数（= 工单受影响人数） |
| `L` / `S` / `R` | int | 仅保留字段位，恒为 0，不再参与定级 |
| `grade` | enum | **A / B / C**（对外的等级口径，不提颜色） |

### 6.3 工单表 `tickets`

| 字段 | 类型 | 说明 |
|---|---|---|
| `ticket_id` | string | 工单编号，如 `TK-20261103092000-B-01` |
| `event_id` | string | 关联事件 |
| `requirement` | string | **可验证的整改动作** |
| `assignee` | string | 区域负责人（接口保留字段；卡片与打印件留空，现场手填） |
| `due_at` | datetime | 整改时限 |
| `review_at` | datetime | 参考复查时间（接口保留；卡片不预排，现场安排） |
| `escalate_at_50pct` | datetime | 时限过半升级提醒时间 |
| `status` | enum | 派单 / 整改中 / 待复查 / 已闭环 / 逾期 |

> 这三张表就是「结果解读」和「价值量化」两页 PPT 的数据来源。
> 没有表，你只能讲感觉；有表，你能出图表：违规趋势、闭环时长分布、逾期率。
> **评委看图表比看文字快十倍。**

### 6.4 工单示例（真实输出）

```
ticket_id            TK-20261103092000-B-01
event_id             EV-20261103092000-B-01
violation            未佩戴安全帽
region               2 号车间高处作业平台
grade                红色
risk                 16
requirement          补发安全帽 1 顶至 2 号车间高处作业平台，
                     登记发放签收记录，次日复查佩戴率
assignee             王志强
cc                   部门安全负责人
created_at           2026-11-03T09:20
due_at               2026-11-03T11:20     ← 2 小时后
review_at            2026-11-04T11:20
escalate_at_50pct    2026-11-03T10:20
status               派单
```

注意 `requirement` 是**可验证的动作**：「补发 X 顶 + 登记签收 + 次日复查佩戴率」，不是「加强管理」这种空话。

### 7.1 关键接口

`Box` 是**模型与引擎的唯一接口**：

```python
@dataclass
class Box:
    label: str          # person / helmet / vest / goggles
    conf: float
    x1: int; y1: int; x2: int; y2: int
    # 派生属性：w / h / area / cx
    # 方法：top_region(ratio) -> 上部区域框
```

只要模型输出能转成 `Box` 列表，引擎就不关心你用的是 YOLO 还是 RT-DETR。

主要函数：

```python
judge_equipment(person, idx, boxes, equip) -> Verdict   # 单装备判定
judge_frame(boxes, equips) -> list[Verdict]             # 单帧全部判定
aggregate_temporal(frames, need=3) -> list[Verdict]     # 时序聚合
likelihood(violation_count_30d) -> int                  # L 值
severity(equip, scene) -> int                           # S 值
grade_of(risk) -> (等级, 处置要求, 时限)                 # 等级映射
build_event(region, equip, ts, conf, evidence) -> Event # 事件构造
make_ticket(ev, affected) -> dict                       # 工单生成
```

### 7.2 推理 API 三个接口

| 接口 | 用途 | 入参 |
|---|---|---|
| `POST /detect` | 表单上传图片 | `file` |
| `POST /detect_b64` | base64，**扣子插件用这个** | `image_base64` |
| `GET /health` | 健康检查 | — |

返回结构与 `Box` 严格对齐：

```json
{"width":1920, "height":1080, "infer_ms":31.2,
 "boxes":[{"label":"person","conf":0.94,"x1":300,"y1":300,"x2":540,"y2":920}]}
```

## 八、扣子工作流怎么搭

### 8.1 五步

1. **部署检测 API**：模型封装 HTTP 服务（本地可先用内网穿透临时对外）
2. **创建 Bot**：把 ② 视觉感知的提示词贴进去
3. **挂知识库**：上传法规 PDF，按条款切分，挂到 ⑤ 合规问答
4. **建工作流**：风险矩阵做成确定性节点（L 查表 → S 查表 → 相乘 → 映射等级）
5. **发布拿链接**：发布为公开访问，链接写进 PPT 第 19 页

### 8.2 第 4 步最容易做错

很多人让大模型自己算等级，结果同一个违规两次算出不同结论。

必须做成工作流里的**确定性节点**。输入同样的确认人数，永远输出同样的等级。

> 这是可复现性的底线，也是答辩时敢让人当场重算的底气。

## 九、已知局限

主动写进 PPT 第 16 页：

| 局限 | 影响 | 优化路径 |
|---|---|---|
| 阈值依赖人工设定，不同厂区像素尺度差异大 | `MIN_PERSON_AREA` 需按相机标定重设 | 提供标定脚本，按已知身高反推像素当量 |
| 只覆盖正面 / 侧面视角 | 完全背影或俯视场景未验证 | 补采背影与俯视数据重新训练 |
| 未做跨镜头人员重识别 | 同一人换镜头会重复计数 | 引入 ReID 特征，或在事件层做时空去重 |
