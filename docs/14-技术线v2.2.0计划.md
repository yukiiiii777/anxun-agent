### 1.3 一个刚发现的事实：0.681 掩盖了 0.565

`data/metrics_real.json` 里一直存着**分类别 AP**，但 README 和技术页只报了总分：

| 类别 | AP@0.5 | npos | tp | fp |
|---|---:|---:|---:|---:|
| person | 0.7971 | 295 | 240 | 57 |
| **helmet** | **0.5645** | 146 | 122 | **131** |
| 合计 mAP50 | 0.6808 | — | — | — |

（`vest` 是另一套权重：`vest` 0.4401 / `novest` 0.4646，见 `data/metrics_vest.json`）

三件事必须自己先说：

1. **0.681 是两类平均，person 拉高的。业务真正要判的 helmet 只有 0.565。**
2. **helmet 的 fp=131，只比真值 npos=146 少 15 个** —— 检测层误检几乎和真值一样密。
   业务误报率能压到 6.12%，是规则层（person 配对 + 三帧窗口 + 几何校验）兜住的，
   **不是检测准**。这句话反过来讲就是本项目的真实卖点：链路稳，不是模型强。
3. **1080p 复验 helmet 0.5634，与 0.5645 差 0.001**（`data/metrics_1080.json`）——
   0.565 是稳定水平，不是 100 张小样本的偶然。

这不是丑闻，是必须自己先摊开的事实。评委只要问一句「分类别呢」，0.681 就撑不住；
主动讲，反而变成「我们知道短板在哪」。

### M1 · 第二数据源独立验证（P0，1 天，本版核心）

**为什么是它**：100 张测试集是所有指标的唯一来源。706 张是同一数据源
（`toborobot/Safety-helmet-dataset`）**从未参与训练**的 test split——
训练只用了它的 train 1200 + valid 400，test 706 一直没动过。

> 已核实：远端 `Phat_project-3/test/` 共 1412 个文件 = 706 图 + 706 标注，
> YOLO 格式，2 类（0=没戴帽 / 1=戴帽），MIT 许可。

**口径必须先写死**（这是 v2.1 翻车的教训——分母/分子必须先定，再跑数）：

| 项 | 706 张能算 | 706 张不能算 |
|---|---|---|
| helmet 单类 AP@0.5 | ✅ 与 `per_class.helmet` 0.5645 直接可比 | |
| 框级误报 / 漏报 | ✅ 以真值框为分母 | |
| 人次级误报 / 漏报（6.12% / 17.20%） | | ❌ 无 person 标注，算不了 |
| 三类 mAP（0.6808） | | ❌ 只有 helmet / nohelmet 两类 |

**所以报告里必须写**：「706 张只验证 helmet 检测层，不验证业务链路」。
两个口径不并列、不混算、不加总。

**做法**：

1. `tools/fetch_helmet_p2.py` 加 `--split test`，拉 706 张到 `datasets/helmet_p2/test/`
   （约 70 MB；`datasets/helmet_p2/` 已在 `.gitignore`，**不入库**）。
   类别沿用脚本现有的 `REMAP = {1: 0, 0: 1}`（原 0=没戴帽 → 我们的 nohelmet，1=戴帽 → helmet）
2. 新写 `tools/eval_second_source.py`：只跑 `models/best.pt`，算 helmet 单类 AP + 框级误报/漏报。
   **必须与主口径同条件**：`imgsz 640` / `conf 0.25` / 同一 AP 算法——否则和 0.5645 不可比
3. **先抽 30 张人工核对标注**（Roboflow 导出，可能有噪声），给「标注可用率」
4. 产出 `data/metrics_second_source.json`，字段结构照 `metrics_real.json`（含 `per_class.helmet`）

**验收**：AP、框级误报、框级漏报三项齐全；30 张核对记录在案；与 100 张同口径的对比表能直接贴 PPT。

> **不预设结论**。掉点也是结论——掉多少就报多少，归因放 M2。

#### 执行记录（11-02 晚，已完成）

**踩到的坑：307 张「空标注」是下载失败，不是负样本。**

首轮拉完，706 张里 307 张标注文件为 0 字节，看起来像负样本。抽 6 张拼图一看——
第一张就是三个戴红帽的工人。追下去：hf-mirror 在并发 16 时返回 **HTTP 429 的 HTML 错误页**，
旧 `fetch_text` 只判 `rc==0`、按行解析时每行字段不够全被跳过，最后写出空文件。
**错误被写成了"负样本"这个语义**，而且脚本还打印"空标注 307"当作正常统计。

修了三处（`tools/fetch_helmet_p2.py`）：
1. `fetch_text` 校验 HTTP 状态码 + 内容特征（`<!DOCTYPE` / `Error 429`），失败返回 `None`
2. `one()` 拿到 `None` 返回 -1，**绝不写空文件**；失败的文件留空以便重跑
3. `fetch` 图片先落 `.tmp` 并校验 JPEG/PNG magic，避免 HTML 存成 `.jpg`

降到 3 并发 + 2s 起步指数退避，重拉 230 张全部成功（915 个框）。最终：**706 张 / 0 张空标注 / 2722 个框**。

**结果（`data/metrics_second_source.json`）**：

| 项 | 100 张主口径 | 706 张第二源 |
|---|---:|---:|
| helmet AP@0.5 | 0.5645 | **0.7501** |
| 真值框 npos | 146 | 1958 |
| 命中 tp | 122 | 1620 |
| 误检 fp | 131 | 738 |
| precision | 0.482 | **0.687** |
| recall | 0.835 | 0.827 |
| 框面积中位数 | 0.0047 | 0.0079 |
| 单帧耗时（GPU） | ≈22 ms | 12.79 ms |

**怎么读这张表**（这是要写进 PPT 的结论）：

1. **召回几乎没变：83.5% → 82.7%**。模型"能检出多少顶帽子"的能力是稳定的，没有漂移。
2. **精确率涨了 20 个点：48.2% → 68.7%**。不是模型变强，是第二源的帽子更大
   （框面积中位数 0.0079 vs 0.0047，大 68%），小目标少了，误检自然少。
3. **所以 0.750 vs 0.565 的差距主要是目标尺度，不是模型好坏。** 这句话必须一起说，
   否则单报 0.750 会被当成"换个数据集反而更好"。
4. **真正的短板在 nohelmet 类**：AP 0.4816、recall **49.4%**、precision 93.3%。
   裸头只检出一半——这是业务漏报的结构性来源，比"把裸头框成帽子"更根本。

> 口径纪律：第二源是**同源独立留出集**（训练用过 toborobot 的 train 1200 + valid 400），
> 不是跨域评测。PPT 上只能说「第二数据源 706 张留出集」，不能说「跨域」。
