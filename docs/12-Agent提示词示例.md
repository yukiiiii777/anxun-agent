## 〇、先说清口径

等级只回答一个问题：**这一单多久内必须处理完。** 唯一依据是**本次确认未佩戴人数**。

| 本次判定 | 等级 | 处理时限 | 是否出整改工单 |
|---|---|---|---|
| 确认未佩戴 **≥3 人** | **A** | 2 小时内 | 出单 |
| 确认未佩戴 **1–2 人** | **B** | 24 小时内 | 出单 |
| 无确认违规，仅**待复核 / 无法判定** | **C** | 7 天内核实 | 进人工核实队列，不派整改单 |
| 全部已佩戴 | 不出单 | — | 直接放行 |

**不看作业类型、不看区域历史违规次数**；同一张图换到哪个区域登记，等级不变。

三组示例取自标准 §2 记录的线上接口实测场景，覆盖 **B / A / 不出单** 三种结果；
C 档在文末单独说明。实测表：

| 场景 | 本次判定 | 等级 | 时限 |
|---|---|---|---|
| 二楼平台 | 1 人未穿反光背心 | **B** | 24 小时内 |
| 装卸区 | 8 人未穿反光背心 | **A** | 2 小时内 |
| 喷漆房 | 5 人未戴安全帽 | **A** | 2 小时内 |
| 通道 | 全部已佩戴 | 不出单 | — |

## 一、三组共用的系统提示词（逐字摘录自线上研判台）

```text
你是「安巡 Agent」，面向厂区安全巡检的研判助手，服务于《安全生产法》与 GB 2811 / GB 39800 体系。

硬规则：
1) 判定只有四态：已佩戴 / 未佩戴 / 待复核 / 无法判定；置信度 {CR} 以下丢弃，
   {CR}–{CF} 转人工复核，不进统计。
2) 处置等级只看「要不要马上处理」，按处理时限分档，**不看作业类型**：
   确认未佩戴 ≥3 人 → A 级（2 小时内）；1–2 人 → B 级（24 小时内）；
   只有待复核/无法判定 → C 级（7 天内核实）；全部已佩戴 → 不出单。
3) 引用法规必须写条款号并给原文；检索不到就写「未检索到」，不许编造条文或文号。
7) 你有四个工具：risk_factors（返回本次判定概况）、grade_risk（按人数给处置等级与时限）、
   law_lookup（查条文原文）、create_ticket（开单，工单号由系统生成）。
   **凡涉及等级或时限，必须先调 grade_risk；不许自己拍等级。**
   引用条文前先调 law_lookup；开工单必须调 create_ticket。
10) **只写本轮上下文里明确给出的事实**：人数与四态、处置等级与时限、工具返回的条文原文。
    没有给出的，一律不写、也不推断——不要补装备种类、数值、人名、地名、部门、班次。
12) 等级对外只用 A/B/C 讲，并且总是带上时限：A 级 = 2 小时内、B 级 = 24 小时内、
    C 级 = 7 天内。不要说「红色/橙色」这套颜色，也不要提 R 值或 L/S——这套口径已经不用了。
13) 工单只说编号、等级、时限、整改要求。整改要求**照抄工具返回值**；
    不要出现任何具体人名或厂区/车间/平台等地名，也不要替某个岗位署名。
```

> `{CR}` / `{CF}` 由 `/api/inspect` 的 `thresholds` 实时注入，页面不写死阈值——
> 这样模型解释判定用的数字与实际推理配置永远一致。

**两个关键工具定义（逐字摘录）**

```text
grade_risk：按「要不要马上处理」给出处置等级 A/B/C 与处理时限
（A=2 小时内、B=24 小时内、C=7 天内），依据是本次确认未佩戴的人数。不需要传参数。

create_ticket：生成整改工单（工单号由系统生成，不要自己编）。
  scene：区域编号，如 A-03（A/B/C 不是场景编号）
  level：处置等级 A / B / C，取自 grade_risk；不要填颜色或 R 值
  action：整改要求
```

**这里藏着本作品最重要的技术选择**：等级不让大模型算，也不让它编工单号。
模型负责理解问题与组织语言，数值判定与编号生成交给确定性代码。

## 二、示例一 · 二楼平台：1 人未穿反光背心 → **B 级 · 24 小时内**

### ① 提示词（用户在研判台输入）

```text
把这张图的违规开一张整改工单，说清楚等级和依据。
```

### ② 输入（真模型接口返回的本次判定概况）

```json
{
  "source": "/api/inspect · best.onnx",
  "verdicts": [
    {"p": "P1", "state": "已佩戴",   "equip": "vest"},
    {"p": "P2", "state": "未佩戴",   "equip": "vest"},
    {"p": "P3", "state": "已佩戴",   "equip": "vest"}
  ],
  "confirmed_not_worn": 1,
  "pending": 0,
  "work_type": "高处作业（仅作背景记录，不参与定级）"
}
```

### ③ 工具调用轨迹（研判台右栏可点开）

```text
risk_factors → 确认未佩戴 1 人 · 待复核/无法判定 0 人
grade_risk   → B 级 · 24 小时内
law_lookup   → 安全生产法 第四十五条（原文）
create_ticket→ 工单号由系统返回
```

### ④ 输出

**四态判定**

| 人员 | 装备 | 结论 | 说明 |
|---|---|---|---|
| P1 | 反光背心 | 已佩戴 | 上身区域内检出装备框 |
| P2 | 反光背心 | **未佩戴** | 上身区域内未检出装备框 |
| P3 | 反光背心 | 已佩戴 | 上身区域内检出装备框 |

**处置等级卡片**

```json
{"code":"B","name":"当日处置","deadline":"24 小时内",
 "why":"本次确认未佩戴 1 人 → 当日完成整改"}
```

**整改工单卡片**

| 项 | 内容 |
|---|---|
| 工单号 | 由 `create_ticket` 返回（系统生成，不由模型编） |
| 等级 / 时限 | **B 级 · 24 小时内** |
| 整改要求 | 现场补发反光背心并核验同班组人员穿戴情况，回传整改照片 |
| 法规依据 | 《中华人民共和国安全生产法》第四十五条（原文经 `law_lookup` 返回） |
| 责任人 / 复查人 / 验收项 | **留空，由现场手填**；画面确认不了，系统不代填 |
| 导出 | 标准 Word《安全隐患整改通知单》，含签署栏，1 页 |

### ⑤ 判读要点

作业类型是「高处作业」，但**等级没有因此升高**——v1.4 起作业类型只是背景记录。
1 人也照样出单；系统把「谁签字、何时验收」的位置留出来，而不是替人签字。

## 三、示例二 · 装卸区：8 人未穿反光背心 → **A 级 · 2 小时内**

### ① 提示词（追问，考察上下文延续）

```text
同一批权重，装卸区这一帧呢？为什么等级变了？
```

### ② 输入

```json
{
  "source": "/api/inspect · best.onnx",
  "confirmed_not_worn": 8,
  "pending": 1,
  "work_type": "车辆通行（仅作背景记录，不参与定级）"
}
```

### ③ 工具调用轨迹

```text
risk_factors → 确认未佩戴 8 人 · 待复核/无法判定 1 人
grade_risk   → A 级 · 2 小时内
create_ticket→ 工单号由系统返回
```

### ④ 输出

**处置等级卡片**

```json
{"code":"A","name":"立即处置","deadline":"2 小时内",
 "why":"本次确认未佩戴 8 人，已不是个别人问题 → 立即处置"}
```

**模型正文（先结论后依据）**

> 本次确认未佩戴 8 人，判 **A 级，2 小时内**处理。
> 与上一单的差别只在人数：1 人属个别问题走当日整改，8 人说明面上已经失控，
> 需要立即停止相关作业。`grade_risk` 的返回值为 A 级 · 2 小时内。
> 另有 1 项待复核，不进违规统计，转人工核实队列。

### ⑤ 判读要点

这条是 v1.4 相对旧矩阵**最想说明的事**：旧口径按区域历史次数定级，
曾出现「1 人少穿背心判 2 小时内、7 人全缺 PPE 判 30 天内」的倒挂。
现在等级随**本次实际人数**走，人数越多处置越急，与现场直觉一致。

追问时模型只回答被问的那一点，没有重贴整张表——这是系统提示词第 14 条在起作用。

## 四、示例三 · 通道：全部已佩戴 → **不出单**

### ① 提示词（考察「不误报」而不是「多报警」）

```text
这一帧有违规吗？需要开工单吗？
```

### ② 输入

```json
{
  "source": "/api/inspect · best.onnx",
  "verdicts": [
    {"p": "P1", "state": "已佩戴"},
    {"p": "P2", "state": "已佩戴"},
    {"p": "P3", "state": "已佩戴"}
  ],
  "confirmed_not_worn": 0,
  "pending": 0
}
```

### ③ 工具调用轨迹

```text
risk_factors → 确认未佩戴 0 人 · 待复核/无法判定 0 人
grade_risk   → 本次无违规，不出等级
（未调用 create_ticket）
```

### ④ 输出

> 本次 3 人全部已佩戴，**无确认违规，不出单**，`grade_risk` 未返回等级，
> 因此没有生成整改工单。

| 项 | 结果 |
|---|---|
| 四态判定 | 3 人全部「已佩戴」 |
| 处置等级 | 无 |
| 整改工单 | **不生成** |

### ⑤ 判读要点

**没有工单也是一次完整研判。** 工业场景里误报几次，安全员就会把告警关掉。
三道无效性保护在这里生效：置信度三档、连续 3 帧时序聚合、小目标拦截。
低置信度只给「待复核」而不硬判违规，小目标直接「无法判定」，都不产生工单。

## 五、C 档补充说明（第四种情形）

三组实测场景里没有出现 C 档，按 v1.4 规则补一句，不要写成实测：

> 若本次**无确认违规，但存在待复核或无法判定项**，`grade_risk` 返回
> `C 级 · 7 天内`，输出 `why = "本次无确认违规，N 项待复核/无法判定 → 7 天内核实"`。
> 它进的是**人工核实队列**，不是整改工单——两者的区别在于「要人去确认」还是「要人去改」。

## 七、现场被问怎么答

- **「提示词能改吗」**：能，改的是角色与措辞；等级、时限、工单号都在代码里，
  模型改不动——这是刻意的，让大模型做算术和编号都不可靠。
- **「换个大模型会变吗」**：判定结果不会变，因为数值判定不经过模型；变的只有措辞。
- **「为什么不用风险矩阵了」**：矩阵的两个输入都答错了问题。L 用区域历史次数，
  同一张图换个区域等级就变；S 用作业类型，回答的是「场景多危险」而不是「多久处理」。
  我们用了四版才把它推翻，改按本次人数与处理时限分档（标准 v1.4 §3）。
- **「为什么工单没有责任人」**：画面确认不了人名与岗位，系统不编。
  输出的是可签署、可追责的通知单，签字栏留给现场——这才是能落地的责任。
- **「提示词里的 {CR} 是什么」**：真实置信度阈值，由推理接口实时注入，
  避免页面写死一个数与模型实际用的数对不上。
