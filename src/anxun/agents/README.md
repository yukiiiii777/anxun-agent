# 安巡 Agent · 多智能体本地实现

> 这一层解决的是仓库里原来空着的那块：`docs/安巡Agent_提示词库.md` 只有五段提示词，
> 扣子/Coze 侧还是「🔴 未开始」。这里的三个 Agent 是**同一套提示词语义的可运行版本**，
> 纯标准库、离线、可复现——答辩现场没网也能演。

## 一、为什么不是「接个大模型就行」

| 做法 | 问题 |
|---|---|
| 把检测框丢给大模型，让它算风险等级 | 大模型做乘法不可靠，同一输入两次结果可能不同，答辩不敢让人当场重算 |
| 只做对话，不接规则引擎 | 就退回成「告警」，作品的核心主张（工单）不成立 |
| 全写在一个脚本里 | 换平台要重写，队友接手看不懂，PPT 讲不出架构 |

所以这里划了一条硬边界：

```
检测模型（可换）  →  规则引擎（确定性）  →  Agent（编排与表达）
 infer_api.py         rules_engine.py       agents/
```

**数值判定全部下沉到 `rules_engine.py`，Agent 只负责三件事**：把判定翻译成人能看懂的结论、
把结论挂上法规依据、把依据变成能验收的动作。这样换模型、换平台、换 UI 都不动业务逻辑。

## 二、三个 Agent 的契约

消息全是 JSON，Agent 之间不共享对象——这是为了将来换成 HTTP 调用时零改动。

### ② 视觉感知 Agent（`perception.py`）

| | |
|---|---|
| 输入 | 连续帧的检测框 `Box(label, conf, x1,y1,x2,y2)` + 帧号 + 时间戳 |
| 输出 | 每人每类装备的四态结论、违规清单、逐帧轨迹 |
| 硬约束 | 只允许四个值：`已佩戴 / 未佩戴 / 待复核 / 无法判定`。「可能未佩戴」这种话在代码层面就不可能输出 |
| 保护 | 置信度三档（≥0.30 定论 / 0.20–0.30 复核 / <0.20 丢弃）、连续 3 帧一致才定论、小目标拦截、遮挡拦截 |

### ③ 隐患研判 Agent（`risk.py`）

| | |
|---|---|
| 输入 | 违规清单 + 区域风险档案（近 30 天违规次数、作业场景、责任人） |
| 输出 | 带 `L / S / R / 等级 / 时限 / 法规依据` 的事件 |
| 硬约束 | `R = L × S` 由 `rules_engine.build_event()` 计算，Agent 不参与算术 |
| 可解释 | 每条事件带三句 `explain`：L 为什么是 4、S 为什么是 4、R=16 为什么落红色 |

### ④ 工单闭环 Agent（`workorder.py`）

| | |
|---|---|
| 输入 | 事件消息（纯 JSON，不依赖上游 Python 对象） |
| 输出 | 工单：整改要求、责任人、SLA、升级路径、验收清单、四段闭环状态 |
| 硬约束 | 时限按等级写死不放宽；复查人 ≠ 整改责任人；整改要求必须过「数量 / 地点 / 留痕」三条检查 |

## 三、怎么跑

在 `src/anxun` 目录下，不装任何依赖：

```bash
python run_agents.py                 # A/B/C 三个场景全跑，终端看完整链路
python run_agents.py --scene B       # 只看高处作业场景
python run_agents.py --json out.json # 顺村落一份结构化结果
python run_agents.py --serve         # 起本地网页，浏览器自动打开 127.0.0.1:8611
```

网页版就是为 PPT 截图准备的：一屏能看到 ②→③→④ 的交接、逐帧圆点、定级表、工单卡、法规原文。

## 四、演示数据想证明什么

同一批人（P1–P5）放进三个机位，故意覆盖五个点：

| 设计 | 想证明 |
|---|---|
| P1 全部合规 | 正常人员不制造噪音 |
| P2 帽置信度 0.35→0.25→0.32→0.28 抖动 | 单帧会误判，时序聚合才定论（结果是「待复核」） |
| P3 无安全帽 | 主违规，进入定级 |
| P4 面积 6000px² / 被遮挡 | 两道失效保护，宁可「无法判定」也不报违规 |
| P5 有帽无背心 | 第二个违规类型，验证 S 值随类型变 |

同一顶安全帽没戴，在三个区域算出三个等级：

| 区域 | 场景 | 30 天违规 | L | S | R | 等级 | 时限 |
|---|---|---|---|---|---|---|---|
| 2 号车间高处作业平台 | 高处 | 7 次 | 4 | 4 | **16** | 🔴 红色 | 2 小时 |
| 3 号车间东侧通道 | 普通 | 4 次 | 3 | 3 | **9** | 🟠 橙色 | 24 小时 |
| 原料库装卸区 | 车辆 | 1 次 | 1 | 2 | **2** | 🔵 蓝色 | 30 天 |

这就是「同样一条告警，不是同一个责任」的实证，也是答辩最该讲的一张表。

## 五、法规依据怎么保证不翻车

`kb.py` 只收**逐字核对过**的条文，文本来源是《中华人民共和国安全生产法》（2021 年第三次修正）：

- 第四十五条：提供符合标准的劳保用品，并**监督、教育**佩戴使用
- 第五十七条：从业人员正确佩戴使用
- 第四十一条：风险分级管控与隐患排查治理（定级方法的出处）
- 第四十六条：经常性检查，「检查及处理情况应当如实记录在案」（工单留痕的出处）
- 第九十九条第（五）项：未提供合规劳保用品的罚则

标准类（GB 2811-2019、GB 39800.1-2020）只登记标准号与适用范围，**不伪造条文原文**。
检索不到时返回 `found=False`，页面直接显示「未检索到直接对应条款」——
这是提示词库里写死的规则，也是现场被查时唯一安全的做法。

## 六、以后要接大模型 / 扣子，改哪里

| 目标 | 改动点 |
|---|---|
| 让 Agent 会聊天 | 在 `cli.py` / `server.py` 外层加一层对话，把 `run()` 的结果作为上下文喂给模型；**不要让模型改数值** |
| 接扣子/Coze | 把 `Orchestrator.run()` 的每段消息换成 HTTP 请求体；`/api/run` 已经是一个现成的接口形状 |
| 换检测模型 | 只改 `infer_api.py`，`Frame(boxes=...)` 的入参格式不变 |
| 真实产线接入 | 把 `scenarios.py` 换成摄像头抽帧；`perception.Frame` 就是适配层 |

## 七、已知局限（写进 PPT 别藏）

- 演示数据是写死的，**不是真实摄像头流**；真实帧率、丢帧、光照变化都未验证
- 时序聚合是「按序号对齐」的简化实现，未做跨帧目标跟踪（ID 关联）
- 责任人、复查人是演示组织架构，未接真实 HR 系统
- 工单状态机只到「派单 / 整改 / 复查 / 归档」四段，没有做审批流与附件上传
- 法规知识库只覆盖 PPE 相关条文，且只核对到条款级，未做全文检索

## 八、文件

| 文件 | 作用 |
|---|---|
| `perception.py` | ② 视觉感知：四态判定、遮挡保护、时序聚合 |
| `risk.py` | ③ 隐患研判：R=L×S、等级、法规依据、可解释文本 |
| `workorder.py` | ④ 工单闭环：SLA、升级、验收检查、状态机 |
| `orchestrator.py` | 编排、留痕、三个场景横向对比 |
| `scenarios.py` | 写死的演示数据（不随机，保证可复现） |
| `kb.py` | 法规知识库（只收核对过的条文） |
| `cli.py` / `server.py` | 终端入口 / 本地网页入口 |
| `web/index.html` | 网页界面（可直接截图进 PPT） |
