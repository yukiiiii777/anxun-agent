一、为什么换掉原来的方向

原方案把整个作品押在「一台自训练的火灾检测模型」上。问题不在于你能不能训练模型——你双卡训练的流程是通的——问题在于 风险过度集中：那台模型是备赛产物，赛后就没有再优化，精度不在最好状态。拿它当唯一支点，等于把成败交付给一个已经放下的东西。

所以这一版换了个支点：不比模型精度，比领域知识的密度。比赛的评委是经济学、管理学背景，他们判断一个作品好坏的标准，很大程度上是「这个团队是不是真的懂这个行业」。而在暖通这一块，你手里有别人编不出来的东西：

39XT1822 卧式组合空调箱 · 外形 3200 × 2304 × 2004 mm · 5 个功能段 · DN80 水管接口 · 额定风量 28000 m³/h

30XAV0532A 风冷 V 型螺杆冷水机组 · 外形 4798 × 2253 × 2297 mm · 制冷量 528 kW · DN125 水管接口 · 8 台风机

—— 这些不是从网上抄的，是你画 CAD 图纸时一个尺寸一个管口核出来的。这就是你的护城河。

核心判断：大多数队伍讲制造业只能讲宏观（产业升级、智能制造），讲不出「DN80 的接口配多大流量」这种颗粒度。你一旦把故事讲到这个层次，评委的第一反应会是「这队真做过工程」，而不是「这队会写 prompt」。这种可信度，比多一个功能值钱得多。

二、选题：为什么是「选型 + 运维」

暖通（HVAC）是建筑能耗的主要构成部分，也是一个典型的「决策在前、成本在后」的行业：选型时算错一个参数，未来十几年的电费都在为这个错误买单。这个特性恰好适合做 Agent——因为它既有知识密集的部分（规范、样本、经验），又有可计算的确定性部分（负荷、风量、管径、能效）。

2.1 痛点

痛点具体表现可论证的抓手
选型靠经验，校核靠手算 中小机电公司做项目，选型多凭老师傅经验翻厂家样本，逐项核对冷量、风量、管径、阻力。样本是 PDF，参数在几十张表里，容易漏项 校核是可复算的，错与对能被客观验证
「大马拉小车」的长期代价 为保证安全裕量，普遍选大一号机组。初投资增加是一次性的，但低负荷运行导致的效率下降是十几年持续发生的 可以算全生命周期成本（LCC），把偏差折算成钱
设备台账散落 设备信息分散在 CAD 图纸、Excel、纸质竣工资料、厂家样本里，交付后运维方拿不到完整台账 台账结构化是可展示的交付物
故障排查依赖原厂 设备报警后只能打厂家售后电话，排查经验留在个人脑子里，人一走知识就没了 故障树推理是有结构的，可以画出来
维保靠人记 维保周期按日历或运行小时，实际执行常超期，直接影响设备寿命与能效 超期率是可量化指标

领域知识现成
AHU 功能段构成、水系统管径、风量与冷量的换算关系——你画图时全都过了一遍。
素材现成
AutoCAD 图纸可直接做 PPT 配图。别的队伍只有截图，你有工程图。

三、系统架构：五个 Agent

按工程流程拆角色，职责单一、输入输出明确。注意第③个 Agent 的设计——这是全篇最关键的技术判断。

① 台账构建 Agent→ ② 选型校核 Agent→ ③ 故障诊断 Agent→ ④ 维保计划 Agent→ ⑤ 规范问答 Agent
Agent职责关键设计（答辩讲这个）
① 台账构建 从厂家样本、设备铭牌、图纸中提取型号、冷量、风量、接口管径、外形尺寸等，建立结构化设备台账 把散落在 PDF 和 CAD 里的信息变成可查询资产，这是后面所有能力的地基
② 选型校核 按房间负荷 → 冷量需求 → 机组选型 → 风量校核 → 水管径核算，输出选型建议与偏差提示 计算全部交给确定性公式引擎，LLM 只负责理解意图和组织参数
③ 故障诊断 根据报警现象（如高压报警、低压报警、水温异常）沿故障树推理可能原因，按概率排序并给排查步骤 不是让模型自由联想，是沿预置故障树走，每个节点有明确的判断条件
④ 维保计划 按运行小时与日历双维度排程，到期提醒、生成工单、记录执行结果 PDCA 闭环，对应管理学语言
⑤ 规范问答 RAG 检索设计规范与设备样本，给出条款原文与出处 每条结论「有出处」，这是可信度来源

四、这一版最强的技术点：把计算从模型手里拿走

这是整个方案里最能让评委眼前一亮的地方，必须单独讲清。

大模型的算术能力是不可靠的。让它算「28000 m³/h 风量配 DN80 水管是否合适」，它可能给你一个听上去很合理但完全错误的答案。

所以本作品的设计原则是：语言归模型，数字归公式。

用户自然语言提问→ LLM 抽取参数→ 调用确定性计算工具→ LLM 解释结果

具体做法：把水流量、流速、管径、冷量、风量、阻力等换算关系封装成独立的计算函数（Python / 公式引擎），Agent 只能调用、不能自由发挥。这样带来三个好处：

  • 结果可复现——同样的输入永远同样的输出，评委当场让你重算也不会翻车
  • 可审计——每个数字都能追溯到用了哪条公式、哪个参数
  • 可防守——被问到「你凭什么这么算」，答案是「按规范的公式算的」，而不是「模型说的」
答辩话术：「我们刻意不让大模型做计算。在工程场景里，一个算错的数字比一个说错的句子危险得多。所以我们把计算全部下沉到确定性工具，模型只负责理解你要什么、以及解释算出来的是什么意思。」

这句话说出来，评委会知道你不是把 AI 当万能膏药贴，而是真的想过它在什么位置可靠、在什么位置不可靠。

五、创新性：官方加分页怎么填

创新点一：计算与语言分离
行业里大量「AI + 工程」产品把计算也交给大模型，导致结果不可复现、无法审计。本作品把工程计算下沉为确定性工具，模型只承担语义层工作，在可靠性与可解释性上是一个实质性改进。
创新点二：全生命周期成本视角
不止算「选多大」，还算「选大了以后多花多少钱」——把初投资、运行电费、维保成本放在同一张表里比较。这是把技术决策翻译成经济决策，正好对上大赛「技术经济」的底色。

独特视角（跨学科）：暖通工程的专业判断 × 运筹与成本分析的经济视角 × 大模型 Agent 的交互范式。三层在一个系统里对齐，对应大赛「横向复合型人才」的取向。

六、数据与知识库

6.1 数据来源

序来源类型怎么用
1厂家设备样本与选型手册企业公开技术资料设备参数、性能曲线、尺寸与接口规格。这是台账构建的原料 需注明样本版本与来源
2国家设计规范国家标准GB 50736《民用建筑供暖通风与空气调节设计规范》、GB 50019《工业建筑供暖通风与空气调节设计规范》等，构成知识库与计算依据 版本与条款号需逐条核实
3真实项目图纸与设备台账一手工程资料39XT1822 AHU、30XAV0532A 冷水机组等实际设备的完整参数，作为案例验证 涉及客户信息需脱敏
4故障案例整理公开技术资料归纳构建故障树，常见报警的现象—原因映射
合规提醒：第 3 项如果来自实际项目，必须脱敏——去掉甲方名称、项目地址、合同金额，只保留设备参数本身。这一点在 PPT 里主动写一句「数据已脱敏」，反而是专业度的体现。

6.2 知识库四层

  • 规范层：设计规范、验收规范、能效标准
  • 产品层：设备样本参数、性能曲线、接口规格
  • 计算层：公式与经验系数（这正是「确定性工具」的来源）
  • 经验层：故障树、常见设计偏差、整改案例

6.3 预处理流程

样本 PDF 解析→ 参数抽取→ 人工校验→ 结构化台账→ 公式引擎挂载

文本侧：规范 PDF → 按条款切分（保留条款号）→ 向量化 → 检索。按条款切分保证检索结果是完整条款，不会断章取义。

参数抽取环节要保留「人工校验」这一步并在 PPT 里画出来——工程参数错一个数字后果严重，全自动抽取不现实，坦诚地做成「AI 抽取 + 人工确认」，比吹全自动更可信。

11.2 评委可能问的问题

  • 「厂家的选型软件已经很成熟了，你凭什么？」→ 不要说替代厂家软件。答案是：厂家软件只算自己家的产品，跨品牌项目要开五个软件；我们做的是跨品牌的统一台账 + 运维侧决策 + 故障诊断，这是厂家软件不覆盖的部分。这个防守必须提前想好，否则一问就塌。
  • 「大模型算错了怎么办？」→ 所以不让它算。计算走确定性公式引擎，结果可复现、可审计。
  • 「数据从哪来？有没有版权问题？」→ 厂家公开样本 + 国家规范 + 自有项目图纸（已脱敏）。样本仅用于参数比对，不做二次分发。
  • 「谁付钱？」→ 中小机电工程公司与物业运维方，按项目或按设备数订阅；替代的是老师傅经验与返工成本。
  • 「这个 Agent 出错会造成工程事故吗？」→ 明确定位为辅助校核工具而非决策依据，所有输出标注「建议值，须由注册工程师复核」。这个责任边界必须在 PPT 里写明。
  • 「为什么选制造不选医疗？」→ 制造是我有真实工程资料和领域知识的方向，能讲出参数级细节；医疗我只能讲框架，讲不到深处。

十二、两方案速览对比

维度衡温 Agent（制造 · 暖通）守净 Agent（医疗 · 院感）
核心能力依赖领域知识 + 确定性计算姿态估计 + 规则引擎
技术实现难度最低，全篇无视觉依赖中低，不需自训高精度检测器，几何时序规则可写，且有分级降级方案
叙事强度中上（LCC 经济账 + 工程颗粒度）高（霍桑效应，方法学批判）
素材准备图纸现成，需建 20–30 台设备台账需自采 50–100 段动作视频
